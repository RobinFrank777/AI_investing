# AI_investing V3.9.0 A0 Architecture Baseline Audit

## Executive Summary

The V3.8.2 production checkpoint is structurally healthy enough for an
incremental `src/` migration, but not for a big-bang move. The repository has
128 root-level Python modules, a 43-module transitive production-pipeline graph,
and several high-fan-out authorities. `config.py` alone has 57 root importers;
`stock_loader.py` has 21. `run_all.py` directly imports 28 project modules.

No genuine multi-module circular import was found by static AST analysis. One
self-component named `daily_report` is caused by the coexistence of
`daily_report.py` and the `daily_report/` package. This namespace collision must
be handled explicitly before either is moved.

The recommended strategy is move-first/redesign-later, one narrow domain per
phase, with root compatibility wrappers and unchanged runtime artifact paths.
The safest first implementation candidate is the research-only, project-import-
free `price_factors.py` module.

## Circular and Suspicious Dependencies

### Circular imports

No genuine multi-module cycle was found. The AST graph reports a self-component
for `daily_report` because root `daily_report.py` imports
`daily_report.generator` while a package with the same top-level name exists.
This name collision is fragile under path/package migration and should be
resolved by a dedicated reporting phase, not opportunistically.

### Suspicious cross-layer edges

- `rank_stocks_v2` imports `report`, `data_readiness`, and `update_data`; it is a
  mixed technical/orchestration/artifact module rather than a clean research
  primitive.
- `portfolio_action_report` and `report_terminal` read `data_readiness` directly.
  This is read-only disclosure, but a future reporting context object would be a
  cleaner boundary; do not redesign it during moves.
- `current_run_status` imports `market_session`; governance observes the data
  session boundary. It must not be allowed to select candidates.
- `run_all` imports every layer and validators. This is legitimate composition
  but makes it the last, not first, migration target.
- `buy_day_replay` imports production decision functions across layers. Its
  explicit read-only/no-write contract must remain tested.
- Backtest modules share technical primitives with production, but no production
  decision module imports a backtest candidate artifact. That boundary is safe.

No data module imports order policy, no technical module transmits orders, and
no decision module falls back to legacy backtest candidates.

## Migration Risk Classification

### LOW

Pure or research-only leaf modules with no artifact authority: `price_factors`,
small factor primitives, selected formatting/chart helpers, demos, and unused
`utils`. Move only one coherent group per phase.

### MEDIUM

Research schemas/pipelines, universe metadata, investment profile helpers,
stock-card builders, shadow/snapshot validators, and validators with several
callers. These need root re-exports and focused import tests.

### HIGH

`config`, every root CLI, universe/data publication authorities,
`stock_loader`, `rank_stocks_v2`, score/signal, candidate adapter/builder,
risk/allocation, sizing/orders, current-run truth, production reporting, and the
`daily_report` namespace. These are artifact producers, production policy
boundaries, or high-fan-out modules.

## Public API Compatibility Plan

For each moved module, the new implementation becomes canonical and the old
root path becomes a pure compatibility re-export:

```python
# price_factors.py (temporary root wrapper)
from src.research.technical.price_factors import (
    calculate_momentum_value,
    calculate_price_factors,
    calculate_trend_value,
    calculate_volatility_20d,
)
```

Rules:

1. Do not keep two implementations.
2. Preserve function names, signatures, constants, exceptions, and return types.
3. Keep root `main()` wrappers and exit codes for scripts.
4. Preserve monkeypatch surfaces used by tests until tests deliberately migrate.
5. Add import-identity/behavior tests before removing any wrapper.
6. Remove wrappers only in a separately approved final consolidation phase.

Especially stable APIs include `calculate_*` score/factor functions,
`run_ranking_pipeline`, candidate/risk builders, allocation/sizing/order builders,
current-run helpers, readiness helpers, and every root CLI `main()`.

## READY Population Maintenance Note

`rank_stocks_v2.run_ranking_pipeline()` builds/saves readiness and passes only
`Ready=True` tickers to `rank_stocks()`. `score.calculate_final_score()` then
computes RS_Score percentiles over that actual DataFrame population.
NearHighScore uses each READY symbol's current history. Coverage disclosure is
produced by `report.py`, `portfolio_action_report.py`, `report_terminal.py`, and
the daily decision composition through `data_readiness.load_readiness_context()`.

A natural future policy location is a governance-owned readiness gate before
ranking, with the statistical policy itself explicitly approved and tested. No
minimum count or percentage is selected here.

## Recommended V3.9.0 Phase Plan

### A1 — Package skeleton and one pure research primitive

Create only the minimal `src` package path required for
`src.research.technical.price_factors`; move that one implementation and retain a
root compatibility re-export. No empty authority packages.

### A2 — Research factor primitives

Move the remaining LOW-risk factor calculation/normalization modules in a small
coherent batch, preserving root paths. Do not move factor orchestration yet.

### A3 — Universe support, then data primitives

Move non-authoritative universe metadata/support first, then loaders and data
readers in separate gates. Move `update_data`, readiness, and session boundary
only after focused publication/freshness tests and a full pipeline gate.

### A4 — Reporting and governance helpers

Move leaf formatting/validation helpers first. Handle the `daily_report`
module/package collision as its own reviewed change. Keep report/current-run
artifact paths unchanged.

### A5 — Research orchestration

Move factor and daily research orchestration plus technical diagnostics. Preserve
RESEARCH_ONLY labeling and all CLIs.

### A6 — Production technical research

Move indicators, score/signal and ranking in narrow steps. Require score
equivalence, READY-subset tests, full suite/pipeline, BUY replay, and NO_ACTION
regression at every authority boundary.

### A7 — Decision chain

Move candidate, risk, allocation, sizing, draft, and review one subdomain at a
time with root wrappers. Do not combine this with policy or schema redesign.

### A8 — Root orchestration consolidation and architecture release audit

Convert root CLIs to verified thin wrappers, inventory remaining compatibility
files, and run final import, artifact, test, pipeline, replay, report-truth, and
Git release audits. Wrapper removal requires a separate human decision.

Every phase requires focused tests, 1120+ full tests, full pipeline, `git diff
--check`, and a human gate. Any production-chain touch additionally requires the
BUY-day replay and NO_ACTION regression.
