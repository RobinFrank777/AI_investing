# AI_investing V3.8.1 Phase 6B-6 Shadow Validation Report

Date: 2026-08-12

Status: non-production validation only. No portfolio consumer or execution path
is connected to the shadow result.

# 1. Purpose

`shadow_validation.py` compares validated production candidates with the
independent point-in-time portfolio risk artifact. It measures exact-key
coverage, validates provenance, classifies risk readiness for research review,
and preserves explicit failure reasons.

`SHADOW_READY` means only that the new candidate/risk path appears complete for
shadow validation. It does not mean BUY approved, portfolio approved, or order
approved. Missing or unclear evidence remains no-action rather than being
filled, inferred, or promoted.

# 2. Architecture

```text
results/validated_portfolio_candidates.csv ----+
                                                | read-only exact-key join
results/portfolio_risk_inputs.csv --------------+
                                                |
                                                v
                                      shadow_validation.py
                                                |
                                                v
                            results/shadow_validation_report.csv
                                      governance review only
```

The implementation reads the two artifacts, copies and validates their data,
and emits a narrow shadow-only CSV. It does not call scoring, signal, portfolio,
position-sizing, order, or reporting modules.

# 3. Join Contract

The only join key is:

```text
Ticker + RunId + AsOfDate
```

Ticker is normalized and AsOfDate is canonicalized before an exact match.
There is no ticker-only, nearest-date, latest-row, fuzzy-date, or forward-fill
fallback. Duplicate composite keys fail the entire validation call with the
explicit code `DUPLICATE_CANDIDATE` or `DUPLICATE_RISK_ROW`.

For an eligible candidate without an exact match, same-ticker evidence is used
only to diagnose `RUN_ID_MISMATCH` or `AS_OF_DATE_MISMATCH`; it is never used as
the candidate's risk row. ScoreModelVersion compatibility is checked after an
exact-key match.

# 4. Shadow Status Rules

| Shadow status | Deterministic rule | Meaning |
|---|---|---|
| `SHADOW_READY` | Eligible candidate, exact key, matching ScoreModelVersion, `RiskStatus=READY`, `RiskValidationStatus=PASS`, and ObservationEndDate <= AsOfDate | Contract appears complete in shadow only |
| `SHADOW_PENDING` | Exact match with `RiskStatus=PENDING` | Required risk evidence is not yet available/current |
| `SHADOW_BLOCKED` | Exact match with BLOCKED, failed/invalid status combination, invalid date, or future ObservationEndDate | Risk evidence fails closed |
| `SHADOW_MISSING_RISK` | Eligible candidate has no exact or diagnosable same-ticker risk row | Required risk row is missing |
| `SHADOW_METADATA_MISMATCH` | RunId, AsOfDate, or ScoreModelVersion is incompatible | Provenance fails closed |

RiskValidationReason is preserved within pending/blocked ShadowReason text.
Unknown combinations cannot become SHADOW_READY. The output does not include
BacktestScore, legacy SharpeRatio, forward-trade MaxDrawdown, RiskLevel,
TargetShares, OrderValue, or OrderAction.

# 7. Failure Reasons

The validator preserves materially different conditions, including:

- `RISK_ROW_MISSING`;
- `RISK_PENDING` plus its source reason;
- `RISK_BLOCKED` plus its source reason;
- `RISK_VALIDATION_FAILED` plus its source reason;
- `RUN_ID_MISMATCH`;
- `AS_OF_DATE_MISMATCH`;
- `SCORE_MODEL_VERSION_MISMATCH`;
- `DUPLICATE_CANDIDATE`;
- `DUPLICATE_RISK_ROW`;
- `FUTURE_OBSERVATION_DATE`;
- `INVALID_RISK_STATUS_COMBINATION`;
- `RISK_ROW_ORPHAN`; and
- `NO_PORTFOLIO_ELIGIBLE_CANDIDATE`.

The programmatic metrics include aggregated failure-reason counts and a
RiskStatus/RiskValidationStatus distribution. Empty source failure text is
made visible as `MISSING_FAILURE_REASON`; it is not collapsed to a generic
available state.

# 8. Multi-Date Validation

Synthetic tests exercise three distinct AsOfDates and three RunIds in one
validation call. Input rows are deliberately unordered; output is ordered
deterministically by AsOfDate, RunId, CandidateRank, and Ticker.

Tests also prove that the same ticker on a different date or under a different
RunId cannot match. Deterministic row counts and SHADOW_READY classifications
are asserted independently of input order. These fixtures validate engine
capability; broader archived multi-regime operational evidence remains required
before consumer migration.

# 11. Remaining Migration Blockers

1. The current zero-eligible snapshot proves safe no-action handling but cannot
   establish non-zero operational coverage.
2. Archived candidate, risk, and pre-trade portfolio snapshots across multiple
   real dates and regimes have not yet been shadow-reviewed.
3. Operational READY/PENDING/BLOCKED rates and recurring failure reasons need
   human review over those archived runs.
4. A future consumer migration still requires separately approved safety
   contracts for all-pending/no-ready states, provenance propagation, and
   removal of legacy production risk dependencies.
5. Portfolio risk levels, multipliers, correlation, sector exposure, and sizing
   behavior remain unapproved and are not supplied by this phase.

Conclusion: the shadow framework is suitable for non-production evidence
collection. Migration remains a separate human-governed decision; when risk
evidence is incomplete, the system continues to prefer explicit no action.
