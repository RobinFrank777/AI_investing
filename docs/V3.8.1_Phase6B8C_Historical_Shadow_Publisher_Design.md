# AI_investing V3.8.1 Phase 6B-8C Historical Shadow Archive Publisher Design

Design date: 2026-08-12

Status: design only. No publisher code or production behavior is introduced in
this phase.

# 1. Purpose

Phase 6B-8C defines a research-only publisher that creates immutable historical
shadow archives from already captured production artifacts.

The publisher is a custody boundary, not a calculation engine. It preserves
the exact evidence it receives, builds integrity metadata, invokes the approved
historical archive validator, and atomically publishes one dated record.

The publisher does not:

- calculate or normalize scores;
- generate or change TradeSignal;
- rerank, filter, promote, or repair candidates;
- calculate or repair risk inputs;
- infer a missing portfolio snapshot;
- create portfolio weights, positions, shares, actions, or orders; or
- claim that an archive PASS authorizes trading.

# 2. Input Boundary

The publisher accepts four already-generated source artifacts:

| Input role | Expected source | Publisher treatment |
|---|---|---|
| Candidate | `production_candidates.csv` | Copy exact bytes to `candidates.csv` |
| Risk | approved portfolio risk output | Copy exact bytes to `risk.csv` |
| Portfolio | `portfolio_snapshot.json` | Copy exact bytes to archive |
| Report | `validation_report.md` | Copy exact bytes to archive |

All inputs are immutable source evidence. The publisher opens them read-only,
records pre-copy hashes, copies bytes without parsing-and-reserializing them,
and verifies post-copy hashes before publication.

## Required preconditions

Before creating a temporary directory, the publisher must establish:

- every input path is explicit, resolves to a regular readable file, and is not
  a directory, symlink escaping the allowed evidence root, or the destination;
- no two input roles resolve to the same path unexpectedly;
- source hashes can be computed twice consistently during a bounded capture;
- candidate RunId, AsOfDate, and ScoreModelVersion are supplied or derived by
  read-only contract inspection without modifying the CSV;
- RiskModelVersion is supplied by the governed risk run and matches risk rows
  when rows exist;
- PortfolioSnapshotId is supplied by the captured portfolio snapshot and
  matches risk rows when rows exist; and
- AsOfDate is a canonical `YYYY-MM-DD` decision date.

Header-only risk data is valid for a zero-eligible scenario. In that case,
RiskModelVersion and PortfolioSnapshotId still must come from explicit governed
run metadata and the portfolio snapshot. They cannot be guessed from empty
rows.

The publisher must not accept live mutable DataFrames as evidence unless they
have first been materialized as immutable source files under a separately
approved capture protocol.

# 3. Output Structure

The publisher creates exactly:

```text
archive/
└── shadow/
    └── YYYY-MM-DD/
        ├── candidates.csv
        ├── risk.csv
        ├── portfolio_snapshot.json
        ├── validation_report.md
        └── manifest.json
```

The final directory name must equal manifest AsOfDate. It contains no lock
file, temporary file, validation JSON, log, backup, or production action
artifact.

Operational logs and failed-attempt records live outside
`archive/shadow/YYYY-MM-DD/`. They must never make an incomplete directory look
canonical.

# 4. Publisher Interface Design

Future implementation should expose a narrow class such as:

```text
HistoricalShadowPublisher
  publish(
    candidate_path,
    risk_path,
    portfolio_snapshot_path,
    validation_report_path,
    archive_root,
    run_metadata,
  ) -> PublishedArchive
```

`run_metadata` is immutable input metadata containing at minimum RunId,
AsOfDate, ScoreModelVersion, RiskModelVersion, and PortfolioSnapshotId. It is
not permission to override conflicting file contents. Any conflict fails the
publication.

Suggested deterministic constant:

```text
PublisherVersion = historical-shadow-publisher-v3.8.1-r1
```

The return object may contain final path, manifest hash, and validator summary.
It must not contain a portfolio recommendation or trading action.

# 5. Atomic Publication Rules

Publishing is a transaction with one visible commit point.

Required sequence:

1. Validate input existence/readability and capture source hashes.
2. Resolve the final target `archive/shadow/{AsOfDate}`.
3. Acquire a publisher lock scoped to the archive root and AsOfDate without
   altering any existing archive.
4. Recheck that the final target does not exist.
5. Create a unique temporary sibling directory, for example:

   ```text
   archive/shadow/.tmp_{RunId}_{random_nonce}/
   ```

6. Copy the four inputs as exact bytes to their contract filenames.
7. Re-hash copied files and compare them with the frozen source hashes.
8. Build canonical `manifest.json` with hashes and provenance.
9. Invoke `HistoricalShadowValidator` on the temporary directory using a
   validator mode that accepts an explicitly expected final AsOfDate while the
   directory still has a temporary name.
10. Require validator `status=PASS` and an allowed evidence scenario.
11. Re-hash all four content files and revalidate the manifest immediately
    before publication.
12. Atomically rename the temporary directory to `{AsOfDate}` on the same
    filesystem.
13. Sync directory metadata where the platform supports durable `fsync`.
14. Release the lock and return the published identity.

The final directory becomes visible only at step 12. Files must not be copied
directly into `{AsOfDate}`.

## Validator integration compatibility

The current Phase 6B-8B validator requires the archive directory name to equal
manifest AsOfDate. A future implementation must not weaken this check globally.
Instead, approve one of these bounded mechanisms:

- validator accepts an `expected_archive_name=AsOfDate` argument only for a
  publisher-owned temporary directory; or
- publisher validates in an isolated staging root whose validation view uses
  the final AsOfDate name and only then performs the same-filesystem atomic
  publish.

Production callers must never gain a flag that disables metadata validation.

# 6. No-Overwrite Rule

If the final target already exists, for example:

```text
archive/shadow/2026-08-12/
```

the publisher raises:

`ArchiveAlreadyExistsError`

This rule applies even when:

- every source hash is identical;
- the prior directory appears incomplete;
- the prior manifest is invalid;
- a human wants to “repair” one field; or
- the new evidence looks more favorable.

The publisher must never:

- overwrite;
- merge;
- update;
- repair;
- delete and recreate;
- rename an existing archive aside;
- follow a “force” option; or
- publish a second canonical record for the same AsOfDate.

Invalid historical archives are handled by a separate append-only governance
disposition. They remain immutable evidence.

## Concurrency rule

Two simultaneous publishers for the same date must have exactly one winner.
The loser receives `ArchiveAlreadyExistsError` or a dedicated
`ArchivePublicationConflictError`; it cannot merge into or inspect-and-repair
the winner's directory.

# 7. Manifest Contract

`manifest.json` must include:

| Field | Requirement |
|---|---|
| `Files` | Exact five-file archive contract list |
| `RunId` | Exact deterministic candidate RunId |
| `AsOfDate` | Exact decision date/final directory name |
| `ScoreModelVersion` | Exact score lineage |
| `RiskModelVersion` | Exact risk lineage |
| `PortfolioSnapshotId` | Exact pre-trade portfolio snapshot identity |
| `CandidateArtifactHash` | SHA-256 of final `candidates.csv` bytes |
| `RiskArtifactHash` | SHA-256 of final `risk.csv` bytes |
| `PortfolioSnapshotHash` | SHA-256 of final `portfolio_snapshot.json` bytes |
| `ValidationReportHash` | SHA-256 of final `validation_report.md` bytes |
| `CreatedTimestamp` | UTC ISO-8601 informational timestamp |
| `PublisherVersion` | Deterministic publisher identifier |

The manifest must also retain archive contract version, repository commit,
PROJECT_VERSION, source filenames or stable source identifiers, source hashes,
and the validator version/result where approved.

## Naming compatibility

Phase 6B-8A used `CreationTimestamp`; this task requires `CreatedTimestamp`.
Phase 6B-8C standardizes the publisher output on `CreatedTimestamp`. During
implementation, the validator and archive schema must be updated together or
the manifest must carry an explicit alias mapping under a new
ArchiveContractVersion. Silent dual meaning is forbidden.

CreatedTimestamp is excluded from RunId, archive identity, candidate/risk
hashes, and decision logic.

## Canonical serialization

- UTF-8 without BOM;
- sorted JSON keys;
- deterministic separators and indentation convention;
- ISO dates and UTC timestamps;
- terminal newline;
- no absolute local paths, credentials, or broker secrets; and
- no self-hash of `manifest.json`, avoiding circular integrity.

# 8. Integrity Requirements

The publisher must verify:

- every input exists and is readable;
- each source can be hashed with SHA-256;
- copied bytes match source hashes;
- required metadata is present and non-conflicting;
- manifest hashes match the copied files;
- final file list is complete and contains no unexpected artifact;
- `HistoricalShadowValidator` returns PASS;
- cross-archive immutability validation returns PASS; and
- the final target remains absent until the atomic rename.

## Source mutation detection

The publisher calculates each source hash before and after copying. If the
source changes during capture, publication fails with a dedicated error such
as `SourceArtifactChangedError`. It cannot retry automatically against the
newer bytes under the same RunId.

## Symlink and path safety

The publisher rejects symlinks for source files, temporary directories, final
targets, and archive-root components where resolution could escape the
approved root. The final rename must remain on the same filesystem to preserve
atomicity.

# 9. Failed Publication and Cleanup

A failed publication:

- leaves no final `{AsOfDate}` directory;
- removes only the unique temporary directory created by that invocation;
- never removes or edits another temporary run;
- never touches an existing canonical archive;
- never writes a PASS evidence report; and
- records a failure outside the archive if operational logging is enabled.

Cleanup must run for missing inputs, read/hash/copy errors, manifest conflicts,
validator failures, source mutation, rename conflicts, and unexpected
exceptions.

If cleanup itself fails, the publisher reports the exact temporary path and a
`CleanupRequired` condition. A `.tmp_*` directory is never counted as evidence
and must be ignored by archive readers and readiness audits.

The publisher must not use broad recursive deletion targets. Cleanup is limited
to the resolved unique temporary directory created by the active invocation.

# 10. Evidence Rules

The publisher creates evidence only. Its outputs may state:

- archive integrity passed;
- source hashes matched;
- metadata was consistent;
- scenario classification from the validator; and
- publication completed atomically.

It cannot claim:

- strategy success;
- investment quality or recommendation;
- BUY or order approval;
- portfolio readiness;
- expected or future performance;
- migration approval; or
- that a PASS archive proves all required historical scenarios exist.

PENDING, BLOCKED, FAILED, missing-risk, and zero-eligible evidence must be
preserved as faithfully as READY evidence. Publisher success describes custody
integrity, not favorable risk status.

# 11. Error Contract

The future implementation should expose stable typed errors:

| Error | Meaning |
|---|---|
| `ArchiveAlreadyExistsError` | Canonical AsOfDate already exists |
| `ArchiveInputMissingError` | Required source file absent |
| `ArchiveInputUnreadableError` | Source cannot be read/hash-verified |
| `SourceArtifactChangedError` | Source changed during capture |
| `ArchiveMetadataMismatchError` | Run/date/model/snapshot metadata conflict |
| `ArchiveManifestError` | Manifest could not be built consistently |
| `ArchiveValidationError` | HistoricalShadowValidator did not PASS |
| `ArchivePublicationConflictError` | Concurrent publish won the final target |
| `ArchiveAtomicPublishError` | Same-filesystem atomic rename failed |
| `ArchiveCleanupError` | Publisher could not remove its temporary directory |

Every error preserves the original cause and identifies the stage without
printing confidential portfolio data.

# 12. Testing Requirements

The future publisher test suite must cover at minimum:

## Successful publication

- valid inputs produce exactly the five expected final files;
- final directory equals AsOfDate;
- temporary directory is absent afterward;
- returned identity matches the manifest; and
- source files remain byte-identical.

## Missing input

- each of the four input roles missing independently;
- error is `ArchiveInputMissingError`;
- no final or temporary archive remains.

## Duplicate archive rejection

- existing final directory causes `ArchiveAlreadyExistsError`;
- identical hashes do not bypass the error;
- existing bytes remain unchanged; and
- no merge/update/repair occurs.

## Hash generation

- each manifest hash equals independently calculated SHA-256;
- source-to-copy hash equality is verified;
- source mutation between reads fails publication; and
- one-byte tampering is detected by validator integration.

## Manifest correctness

- all required identity/hash/timestamp/version fields are present;
- Files lists the exact five-file contract;
- directory, RunId, models, and snapshot agree with artifacts;
- CreatedTimestamp is valid UTC and informational only; and
- canonical JSON is deterministic apart from CreatedTimestamp.

## Atomic failure cleanup

- injected copy, hashing, manifest, validator, and rename failure;
- no canonical directory becomes visible;
- only the publisher's own `.tmp_*` is cleaned;
- pre-existing archives and unrelated temp directories are unchanged; and
- cleanup failure is reported explicitly.

## Validator integration

- publisher refuses to rename unless `HistoricalShadowValidator` returns PASS;
- candidate hash mismatch is rejected;
- metadata mismatch is rejected;
- missing eligible risk is rejected;
- invalid RiskStatus is rejected;
- immutability conflict is rejected; and
- ZERO_ELIGIBLE, SINGLE_ELIGIBLE, MULTIPLE_ELIGIBLE, and RISK_BLOCKED valid
  archives retain their scenario without becoming trading actions.

## Additional safety tests

- concurrent same-date publication has one winner;
- symlink/path traversal is rejected;
- archive readers ignore `.tmp_*` directories;
- no production module imports publisher code; and
- no output contains TargetShares, OrderValue, OrderAction, or brokerage data.

# 13. Production Boundary

The publisher remains outside:

- `portfolio_risk.py`;
- `position_sizing.py`;
- `order_draft.py` and `order_review.py`;
- `daily_decision_report.py`;
- scoring and signal generation; and
- candidate and risk calculation.

No production trading path imports the publisher, calls it automatically, or
reads from `archive/shadow/`. A future operational scheduler, if approved,
must invoke it after source artifacts are finalized and outside the order path.

Failure to publish an archive must not stop, retry, or alter production trading
logic in this phase. It creates a validation-evidence gap that readiness audits
must report explicitly.

# 14. Acceptance Criteria

Phase 6B-8C design is complete when:

1. immutable input and output boundaries are explicit;
2. the exact archive structure and manifest contract are defined;
3. atomic staging, validator integration, rename, and cleanup rules are
   specified;
4. existing archives always fail with ArchiveAlreadyExistsError;
5. source mutation and cross-archive immutability checks are required;
6. successful publication is clearly separated from strategy or trading
   approval;
7. required tests cover success, missing input, duplicate archive, hashes,
   manifest, cleanup, and validator integration;
8. no Python or production module is changed; and
9. human review approves the design before implementation.

Design conclusion: the publisher's job is to preserve evidence, including
uncomfortable evidence, without interpretation. The safest publisher is one
that can fail cleanly, leaves no partial history, and has no mechanism to
rewrite the past.
