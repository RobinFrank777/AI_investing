## Current Flow

```text
Canonical OHLCV CSV
  ↓ stock_loader.load_stock
Technical indicators
  ↓ indicators.calculate_indicators
Latest observations and trailing returns
  ↓ rank_stocks_v2.process_single_stock
Unweighted score components
  ↓ score.calculate_rank_score_diagnostics
Weighted RawScore (existing column: Score)
  ↓ score.calculate_final_score
Cross-sectional 60-day percentile (RS_Score) + NearHighScore
  ↓ 70% RawScore + 20% RS_Score + 10% NearHighScore
FinalScore
  ↓ trade_signal.generate_signals
BUY / WATCH / IGNORE
  ↓ descending FinalScore sort
Ranked output
```

There is no general normalization step for TrendScore, MomentumScore,
VolumeScore, RiskScore, or RawScore. The only cross-sectional normalization is
`RS_Score`, calculated as the percentile rank of `60Day_Return` among the
symbols processed in that run.

## Component calculation

### Market inputs and technical indicators

`rank_stocks_v2.process_single_stock()` loads canonical OHLCV through
`stock_loader.load_stock()` and calls `indicators.calculate_indicators()`.
The score path consumes latest Close, MA20, MA60, High60, High252, Volume,
VolumeMA20, MACD, MACD signal, MACD histogram, and trailing Close returns.

- `20Day_Return = Close[-1] / Close[-20] - 1`
- `60Day_Return = Close[-1] / Close[-60] - 1`
- `Volume_Ratio = latest Volume / VolumeMA20`
- `DistanceToHigh = latest Close / High252`

### TrendScore

Calculated in `score.calculate_rank_score_diagnostics()` using the unchanged
rules formerly embedded in `calculate_rank_score()`:

- +30 when Close > MA20
- +30 when MA20 > MA60
- +20 when Close > High60
- +30/+20/+10 for DistanceToHigh at least 0.95/0.90/0.80

The branches are additive except the DistanceToHigh tiers, which are mutually
exclusive. Observed theoretical range is 0 to 110.

### MomentumScore

The existing score is now exposed as two diagnostic subcomponents:

- `ReturnMomentumContribution = 70 × 20Day_Return + 30 × 60Day_Return`
- `MACDContribution`:
  - +20 when MACD > MACD signal
  - +10 when MACD > 0
  - +10 when MACD histogram > 0

`MomentumScore = ReturnMomentumContribution + MACDContribution`.

These names expose existing arithmetic; they do not add factors or change
weights.

### VolumeScore

- +20 when Volume_Ratio > 1.5
- otherwise +10 when Volume_Ratio > 1.0
- otherwise 0

### RiskScore

`RiskScore` is unconditionally 50 for every processed stock. It does not read a
risk metric.

### RawScore

The pre-existing `Score` formula is:

```text
RawScore =
    0.40 × TrendScore
  + 0.25 × MomentumScore
  + 0.20 × VolumeScore
  + 0.15 × RiskScore
```

For backward compatibility, the ranked table retains `Score`; Phase 3 also
exposes the identical value as `RawScore`.

### RSScore and NearHighScore

`score.calculate_final_score()` calculates:

- existing `RS_Score = percentile rank(60Day_Return) × 100`
- `NearHighScore = 40/30/20/10/0` for DistanceToHigh bands of at least
  1.00/0.98/0.95/0.90/below 0.90

The diagnostic CSV exposes `RS_Score` under the requested name `RSScore`. No
calculation was renamed in production.

### FinalScore

```text
FinalScore = 0.70 × Score + 0.20 × RS_Score + 0.10 × NearHighScore
```

Stocks are sorted by descending FinalScore after signal classification. No
explicit persistent Rank column is generated in this pipeline; row order is the
rank order.

## Threshold application

`trade_signal.generate_signals()` applies the unchanged rules:

- default: IGNORE
- FinalScore >= 60: WATCH
- BUY requires all of:
  - FinalScore >= 75
  - Volume_Ratio > 0.8
  - DistanceToHigh >= 0.95
  - Close > MA20
  - MA20 > MA60

The later BUY assignment overrides WATCH when all BUY conditions hold.

## Diagnostic behavior

Phase 3 adds `results/score_diagnostics.csv` with exactly:

`Ticker, Date, TrendScore, MomentumScore, MACDContribution,
ReturnMomentumContribution, VolumeScore, RiskScore, RawScore, RSScore,
NearHighScore, FinalScore`.

`Date`, `RawScore`, and `RSScore` are diagnostic aliases for the existing
`MarketDataDate`, `Score`, and `RS_Score` concepts. Missing required component
columns raise a `ValueError` listing the missing columns. Missing cell values
are preserved as missing; the diagnostic builder does not impute or invent a
value.

## Score model version metadata recommendation

Future quantitative outputs should include a `ScoreModelVersion` field once a
formal model-versioning contract exists. A value such as
`technical-score-v3.8.1` would make formula provenance explicit and separate
the score model from the application release. It is not implemented in Phase 3
because the existing ranking-output architecture has no score-model metadata
contract and the requested phase forbids runtime-behavior expansion.
