# AI_investing V3.8.1 Phase 6B-8E1 Portfolio Snapshot Provenance Design

Design date: 2026-08-13

Status: design only. This document creates no portfolio snapshot, production
artifact, historical evidence, portfolio action, or order. It does not modify
scoring, signals, risk calculations, position sizing, or production consumers.

# 1. Purpose and Boundary

Phase 6B-8E1 defines a governed provenance bridge between one validated
candidate run and the exact pre-action portfolio state used by point-in-time
risk assessment.

The required boundary is:

```text
validated_portfolio_candidates.csv
  + authoritative pre-action portfolio state
  -> governed portfolio snapshot capture
  -> immutable portfolio_snapshot.json
  -> point-in-time risk calculation
  -> portfolio_risk_inputs.csv
  -> shadow validation and historical archive
```

The bridge answers only:

> Which exact portfolio state was available for this candidate RunId at its
> decision boundary?

It does not decide whether a security is attractive, eligible, risk-ready,
sized, approved, or ordered. A valid snapshot is necessary provenance for risk
assessment; it is never sufficient authority for a portfolio action.

# 2. PortfolioSnapshotId Contract

`PortfolioSnapshotId` is a deterministic identifier for the canonical
pre-action portfolio state at one PortfolioAsOfDate.

Required format:

```text
portfolio-snapshot-{YYYYMMDD}-{hash_prefix}
```

where:

- `YYYYMMDD` is canonical PortfolioAsOfDate;
- `hash_prefix` is the first 12 lowercase hexadecimal characters of
  `PortfolioStateHash`; and
- `PortfolioStateHash` is the full SHA-256 digest defined in Section 7.

Example format only—not production evidence:

```text
portfolio-snapshot-YYYYMMDD-abcdef123456
```

The identifier must be derived by the governed snapshot writer. Callers may
not supply, edit, randomize, or reuse it to make metadata match. It must not be
derived from filesystem path, modification time, capture timestamp, candidate
score, risk result, or future portfolio action.

## Identity invariants

1. Identical canonical portfolio state and PortfolioAsOfDate produce the same
   PortfolioSnapshotId.
2. Any change to holdings, quantities, cash, currency, valuation inputs, or
   required state metadata changes PortfolioStateHash and therefore the ID.
3. The ID identifies captured state, not freshness or approval.
4. ID prefix collision is treated as a governance conflict and requires the
   full hash comparison; it must never select an arbitrary snapshot.
5. A missing or unverifiable ID blocks risk assessment.

# 3. RunId Linkage

The snapshot provenance envelope must carry the exact candidate `RunId` from
`validated_portfolio_candidates.csv`. Phase 6B-8E1 permits one candidate RunId
per snapshot artifact and one PortfolioSnapshotId per candidate RunId.

Required linkage rules:

- RunId is copied exactly after candidate contract validation.
- All non-empty candidate rows must contain one identical RunId.
- The snapshot writer must not generate or repair candidate RunId.
- The snapshot envelope, risk artifact, validation report, and archive manifest
  must carry the same RunId.
- A snapshot from a prior, later, or otherwise different RunId cannot be joined
  even if tickers, holdings, or dates look identical.
- Joining on Ticker, date, “latest,” filename, or PortfolioSnapshotId alone is
  forbidden.

The governed risk linkage is:

```text
candidate RunId + candidate AsOfDate + PortfolioSnapshotId
```

Risk rows additionally join candidates on exact `Ticker + RunId + AsOfDate`.
PortfolioSnapshotId proves which portfolio context was used; it does not
replace the candidate join key.

# 4. AsOfDate and PortfolioAsOfDate Rules

Two dates have distinct meanings:

| Field | Meaning | Rule |
|---|---|---|
| `AsOfDate` | Candidate decision and market-data cutoff | Exact candidate value; valid ISO `YYYY-MM-DD`; one value per RunId |
| `PortfolioAsOfDate` | Effective date of the captured pre-action holdings/cash state | Valid ISO date or approved timestamp; must be no later than AsOfDate |
| `CapturedTimestamp` | Informational UTC capture time | Must not determine state identity, joins, or decision eligibility |

For the first contract, PortfolioAsOfDate should equal AsOfDate unless an
approved operating calendar explicitly permits a prior effective portfolio
date. A prior date must be retained exactly and evaluated under a governed
staleness policy. It must never be relabeled as AsOfDate.

Forbidden date behavior includes:

- future portfolio state (`PortfolioAsOfDate > AsOfDate`);
- substituting the nearest, latest, or next available snapshot;
- backdating a state captured after later holdings changes;
- using filesystem mtime as an economic date;
- repairing an invalid date; and
- treating CapturedTimestamp as evidence that holdings were known earlier.

If no authoritative state exists at or before AsOfDate, snapshot provenance is
unavailable and the run fails closed.

# 5. Candidate Artifact Relationship

Authoritative candidate input:

`results/validated_portfolio_candidates.csv`

The provenance bridge reads candidate identity only. It must not change or
recalculate CandidateRank, FinalScore, TradeSignal, Eligibility,
PortfolioEligible, ValidationStatus, or ValidationReason.

## Candidate preconditions

- stable candidate schema exists, including zero-row/zero-eligible cases;
- Ticker is normalized and unique;
- RunId, AsOfDate, and ScoreModelVersion are present and uniform;
- the candidate artifact has a recorded SHA-256;
- all PortfolioEligible values have already passed the candidate adapter; and
- candidate bytes remain unchanged throughout snapshot binding.

The snapshot provenance envelope records:

- `RunId`;
- `AsOfDate`;
- `ScoreModelVersion`;
- `CandidateArtifactHash`; and
- `CandidateRowCount` and `PortfolioEligibleCount` for audit context.

These fields bind the portfolio snapshot to the exact candidate artifact but
are excluded from portfolio state values. Candidate hash changes require a new
binding and cannot be repaired inside an existing snapshot.

Zero eligible candidates still require a real portfolio snapshot for complete
historical provenance. “No eligible candidate” does not prove “empty
portfolio,” and it does not authorize an invented PortfolioSnapshotId.

# 6. Risk Artifact Relationship

The point-in-time risk calculator may consume the snapshot only after the
snapshot contract and candidate binding pass validation.

Every populated risk row must preserve:

- candidate Ticker, RunId, AsOfDate, and ScoreModelVersion;
- exact PortfolioSnapshotId;
- exact PortfolioAsOfDate;
- approved RiskModelVersion; and
- ObservationEndDate no later than AsOfDate.

`CurrentPortfolioWeight` and any future exposure/correlation fields must be
calculated from the exact snapshot identified by PortfolioSnapshotId. They
must not use a later live portfolio, the proposed order, a model portfolio, or
legacy backtest output.

For zero PortfolioEligible candidates, risk output may remain header-only. The
snapshot and manifest must still carry RiskModelVersion and
PortfolioSnapshotId explicitly; those values cannot be inferred from absent
risk rows.

A risk artifact is invalid when it:

- mixes PortfolioSnapshotId values within one RunId/AsOfDate;
- references a snapshot whose hash or candidate binding fails;
- omits snapshot identity on READY/PASS rows;
- uses PortfolioAsOfDate after AsOfDate; or
- contains a portfolio-derived value that cannot be reproduced from the bound
  snapshot.

# 7. Portfolio State Contract and Hash

The proposed artifact is canonical UTF-8 JSON named
`portfolio_snapshot.json`. It has a provenance envelope and a state payload.

## Required provenance envelope

| Field | Requirement |
|---|---|
| `PortfolioSnapshotContractVersion` | Deterministic schema identifier |
| `PortfolioSnapshotId` | Deterministic ID derived from state hash |
| `PortfolioStateHash` | Full lowercase SHA-256 digest |
| `RunId` | Exact candidate RunId |
| `AsOfDate` | Exact candidate decision date |
| `ScoreModelVersion` | Exact candidate score lineage |
| `CandidateArtifactHash` | SHA-256 of bound candidate bytes |
| `PortfolioAsOfDate` | Effective pre-action portfolio-state date |
| `PortfolioSourceId` | Governed non-secret identifier for the authoritative source |
| `BaseCurrency` | Required controlled ISO currency code |
| `CapturedTimestamp` | Informational UTC timestamp, excluded from state identity |
| `RepositoryCommit` | Code provenance for the capture tool |

## Required state payload

- normalized holdings with at minimum Ticker, settled quantity, and governed
  valuation price/date when valuation is part of risk;
- cash balances by currency;
- total portfolio value under the approved valuation convention;
- explicit empty holdings array when the authoritative source proves no
  holdings; and
- controlled source status and reconciliation status.

Unknown quantities or cash are missing evidence, not zero.

## Canonicalization and PortfolioStateHash

Before hashing:

1. validate types, currency, dates, finiteness, and uniqueness;
2. normalize Ticker and currency identifiers under governed conventions;
3. sort holdings by Ticker and cash balances by currency using stable ordering;
4. serialize the state payload plus PortfolioAsOfDate, PortfolioSourceId,
   BaseCurrency, valuation convention/version, and snapshot contract version;
5. use UTF-8 without BOM, sorted JSON keys, deterministic separators, and no
   insignificant platform-dependent values; and
6. calculate SHA-256 from those canonical bytes.

`PortfolioSnapshotId`, RunId, candidate scores, CandidateArtifactHash,
CapturedTimestamp, host paths, and later risk results are excluded from
PortfolioStateHash. This avoids circular identity and keeps the state identity
independent of the candidate evaluation. The full published artifact receives
its own separate archive hash in the historical manifest.

Floating-point values require an approved decimal representation; binary float
string behavior must not define canonical state. Secrets, account credentials,
and personally identifying broker data must never enter the snapshot or hash
payload.

# 8. Immutable Snapshot Rules

1. Capture writes to a unique temporary sibling path and publishes atomically.
2. Inputs are read-only and hashed before and after capture; mutation aborts.
3. An existing PortfolioSnapshotId/RunId binding cannot be overwritten,
   merged, refreshed, or repaired.
4. A canonical snapshot cannot be regenerated from later holdings and labeled
   with an earlier AsOfDate.
5. Corrections use a new snapshot plus an append-only disposition referencing
   the invalid artifact; the original bytes remain preserved.
6. Snapshot, candidate, risk, validation, and archive hashes are verified at
   every custody boundary.
7. A deterministic rerun from the same frozen authoritative state must produce
   the same PortfolioStateHash and PortfolioSnapshotId, excluding only approved
   informational timestamps from artifact-byte equality.
8. Partial writes, missing files, or failed validation never become canonical
   evidence.
9. Snapshot discovery by modification time, filename guessing, or “latest” is
   forbidden; consumers require explicit identity.
10. Research/test fixtures live outside the production evidence archive and
    are permanently labeled `TESTING`.

# 9. Point-in-Time Requirements

The snapshot must describe portfolio state before any action arising from the
bound candidate run.

Required controls:

- authoritative source extraction is bounded to PortfolioAsOfDate;
- pending/unsettled activity is represented under an approved convention, not
  silently omitted;
- valuation prices and FX rates record ObservationDate and never exceed
  AsOfDate;
- later fills, cancellations, deposits, withdrawals, holdings, or cash changes
  cannot affect the earlier snapshot;
- proposed candidate trades are excluded from current holdings and weights;
- portfolio state from a future run cannot be backfilled;
- source availability time is retained when economic date alone is
  insufficient; and
- rerunning after future source mutations must reproduce the earlier result
  from frozen evidence or fail as unavailable.

For historical reconstruction, a later statement cannot be reverse-engineered
into an earlier portfolio snapshot unless the authoritative source itself
provides immutable as-of records and the reconstruction method is separately
approved. Missing historical state is reported `NOT AVAILABLE`.

# 10. Failure States and Fail-Closed Outcomes

| Failure code | Condition | Required outcome |
|---|---|---|
| `SNAPSHOT_SOURCE_NOT_AVAILABLE` | No authoritative pre-action state exists | BLOCK; no snapshot identity |
| `SNAPSHOT_SOURCE_UNREADABLE` | Source cannot be read consistently | BLOCK |
| `SNAPSHOT_SOURCE_CHANGED` | Source hash changes during capture | BLOCK; remove only partial capture |
| `CANDIDATE_METADATA_MISSING` | RunId, AsOfDate, or ScoreModelVersion absent | BLOCK |
| `CANDIDATE_METADATA_MIXED` | Candidate artifact contains conflicting provenance | BLOCK |
| `CANDIDATE_HASH_MISMATCH` | Bound candidate bytes differ | BLOCK |
| `RUN_ID_MISMATCH` | Snapshot/risk RunId differs from candidate RunId | BLOCK |
| `AS_OF_DATE_MISMATCH` | Snapshot/risk decision date differs | BLOCK |
| `FUTURE_PORTFOLIO_STATE` | PortfolioAsOfDate exceeds AsOfDate | BLOCK |
| `STALE_PORTFOLIO_STATE` | State exceeds approved staleness limit | PENDING or BLOCK per approved policy; never READY |
| `INVALID_PORTFOLIO_VALUE` | Missing, non-finite, inconsistent, or out-of-range state value | BLOCK |
| `DUPLICATE_HOLDING` | Normalized Ticker occurs more than once without approved lot aggregation | BLOCK |
| `PORTFOLIO_RECONCILIATION_FAILED` | Cash, holdings, or total value cannot reconcile | BLOCK |
| `PORTFOLIO_STATE_HASH_MISMATCH` | Canonical state does not match recorded hash | BLOCK |
| `PORTFOLIO_SNAPSHOT_ID_MISMATCH` | ID does not derive from hash/date | BLOCK |
| `SNAPSHOT_ALREADY_EXISTS` | Immutable target identity already exists | BLOCK; no overwrite |
| `SNAPSHOT_PUBLICATION_CONFLICT` | Concurrent capture targets the same identity | Exactly one winner; loser BLOCKED |
| `RISK_SNAPSHOT_MISMATCH` | Risk artifact references another snapshot | BLOCK risk/shadow readiness |
| `SNAPSHOT_NOT_AVAILABLE_HISTORICALLY` | Historical state cannot be proven | Report `NOT AVAILABLE`; do not reconstruct |

Failure must preserve cash/no-action semantics. No default empty portfolio,
zero weight, guessed cash, prior snapshot, or fabricated ID may convert a
failure into READY.

# 11. Research-Only and Non-Ordering Boundary

The provenance bridge is research, validation, and evidence infrastructure
only. It remains outside:

- candidate scoring and TradeSignal generation;
- candidate eligibility decisions;
- risk formulas and risk thresholds;
- portfolio construction and position sizing;
- order draft, review, approval, routing, and execution;
- daily production decision authority; and
- brokerage accounts and live capital.

The bridge must never:

- create a BUY, WATCH, IGNORE, or eligibility state;
- calculate a target weight, shares, order value, or order action;
- submit, approve, cancel, or modify an order;
- alter holdings or cash at the source;
- interpret a valid snapshot as permission to invest; or
- turn synthetic fixtures into production evidence.

`SNAPSHOT_VALID` means only that identity, state, timing, reconciliation, and
integrity meet the snapshot contract. `RISK READY` remains a separate
diagnostic state, and neither status authorizes a portfolio or brokerage
action.

# 12. Implementation Gate and Remaining Decisions

No implementation is authorized by this design. Before a future implementation
phase, human governance must approve:

- the authoritative portfolio source and access method;
- holdings, cash, valuation, pending-activity, FX, and reconciliation schema;
- PortfolioAsOfDate granularity and staleness policy;
- decimal canonicalization and valuation conventions;
- snapshot contract/version identifiers;
- secure handling and redaction rules;
- storage layout and retention/disposition policy; and
- explicit compatibility with the existing risk calculator, historical
  publisher, and validator without weakening their behavior.

Design decision: **PROVENANCE CONTRACT DEFINED — NO SNAPSHOT OR ORDER AUTHORITY**.
