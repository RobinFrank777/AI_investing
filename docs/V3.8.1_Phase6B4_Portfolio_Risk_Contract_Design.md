# AI_investing V3.8.1 Phase 6B-4 Portfolio Risk Contract Design

Design date: 2026-08-12

Status: design only. No risk calculator, formula, threshold, portfolio behavior,
position sizing, order logic, scoring, or version metadata is changed here.

# 1. Risk Boundary

The risk contract sits after production candidate validation and before
portfolio construction:

```text
validated_portfolio_candidates.csv
  -> candidate eligibility boundary
  -> point-in-time risk calculator
  -> portfolio_risk_inputs.csv
  -> risk contract validator
  -> candidate/risk provenance join
  -> risk-ready portfolio candidates
  -> portfolio construction
```

Its sole question is:

> Can this already-eligible security be added to this portfolio now, given
> current market conditions, liquidity, existing exposure, and data quality?

It must not answer whether a stock is attractive, recalculate FinalScore,
change TradeSignal, select a threshold, or use future performance. It must not
create BacktestScore or reuse legacy strategy-return statistics.

## Responsibility ownership

| Responsibility | Owner |
|---|---|
| Technical score and BUY/WATCH/IGNORE | Existing scoring and signal modules |
| Candidate eligibility | Production candidate builder and candidate adapter |
| Point-in-time market/liquidity measurements | Future risk calculator |
| Current holdings/exposure snapshot | Future portfolio-state provider |
| Risk readiness and assessment | Future risk evaluator/validator |
| Weight and holding selection | Portfolio construction |
| Shares and dollars | Position sizing |
| Draft/review approval | Order workflow |

The conservative design principle is that uncertainty is not a low-risk value.
Missing or incomprehensible risk information must preserve cash and block
construction rather than be zero-filled.

# 2. Candidate vs Portfolio Risk Separation

## Candidate eligibility

Candidate eligibility asks: **“Should this security be considered?”**

Current authoritative inputs are:

- `FinalScore`;
- `TradeSignal`;
- `CandidateRank`;
- source `Eligibility`; and
- validation/provenance metadata.

Only production BUY plus ELIGIBLE currently becomes PortfolioEligible at the
candidate boundary. WATCH and IGNORE remain non-eligible.

Investment Profile is currently presentation-only. It may help a human
understand company context, but Phase 6B-4 does not authorize it to affect
eligibility, risk status, sizing, or orders. Free-form thesis, moat, rating, or
risk text is not a reproducible quantitative risk input.

## Portfolio risk assessment

Portfolio risk asks: **“Can this eligible security be added to this portfolio
now?”**

Its possible inputs include:

- trailing volatility and drawdown known at AsOfDate;
- current liquidity and price coverage;
- current portfolio position and sector concentration;
- correlation using only history through AsOfDate;
- configured exposure limits; and
- separately governed structured fundamental-risk data.

## Why separation is mandatory

1. A strong signal may still be too illiquid, concentrated, or correlated for
   the current portfolio.
2. Risk conditions change without changing the investment signal.
3. Candidate ranking is cross-sectional security selection; risk assessment
   depends on current holdings and capital.
4. Mixing risk into eligibility would silently change the production signal
   model and threshold semantics.
5. Mixing signal strength into risk would allow a high score to excuse missing
   or dangerous risk data.
6. Separate statuses make “eligible but risk pending” auditable and allow a
   safe cash/no-action outcome.

Candidate eligibility is necessary but not sufficient. Construction requires:

```text
PortfolioEligible == True
AND RiskStatus == READY
AND ValidationStatus == PASS
```

# 3. Risk Contract Definition

Proposed artifact: `results/portfolio_risk_inputs.csv`.

Row grain: one assessment per eligible Ticker for one candidate RunId,
AsOfDate, portfolio snapshot, and RiskModelVersion.

## Identity and provenance

| Field | Type / invariant | Purpose |
|---|---|---|
| `Ticker` | Required normalized unique string | Join key |
| `AsOfDate` | Required ISO date | Market-data cutoff |
| `RunId` | Required; exact candidate RunId | Prevent cross-run mixing |
| `ScoreModelVersion` | Required; exact candidate value | Candidate lineage |
| `RiskModelVersion` | Required deterministic string | Risk formula governance |
| `PortfolioSnapshotId` | Required deterministic identifier | Identifies holdings/cash state |
| `PortfolioAsOfDate` | Required ISO date/time | Portfolio-state cutoff |
| `CalculationTimestamp` | Required timestamp | Operational audit trail; not a data cutoff |
| `ObservationEndDate` | Required date, <= AsOfDate | Proves trailing inputs stop in time |

## Market risk

| Field | Meaning |
|---|---|
| `Volatility20D` | Trailing return volatility through AsOfDate under approved convention |
| `Volatility60D` | Longer trailing return volatility through AsOfDate |
| `TrailingDrawdown` | Current decline from trailing-window peak, not future trade drawdown |
| `ATR14` | Current trailing ATR from canonical OHLCV |
| `RiskObservationCount` | Valid observations supporting calculations |

## Liquidity

| Field | Meaning |
|---|---|
| `AverageVolume20D` | Trailing mean share volume |
| `AverageDollarVolume20D` | Trailing mean Close × Volume |
| `LiquidityCoverage` | Count/ratio of valid observations |
| `SpreadProxy` | Optional approved OHLCV-based proxy, explicitly labeled approximate |

## Portfolio context

| Field | Meaning |
|---|---|
| `CurrentPortfolioWeight` | Existing ticker exposure before proposed trade |
| `CurrentSectorExposure` | Existing sector exposure under approved taxonomy |
| `CorrelationToPortfolio60D` | Trailing correlation to current portfolio returns |
| `CorrelationObservationCount` | Valid overlapping observations |
| `ProposedSlotConcentration` | Diagnostic concentration if one configured slot is used; not an approved weight |

## Fundamental and structural risk

No free-form Investment Profile field belongs in the quantitative contract.
A future separately sourced, structured fundamental-risk assessment may expose:

- `FundamentalRiskStatus`;
- `FundamentalDataAsOfDate`;
- `FundamentalRiskModelVersion`; and
- explicit structured inputs such as leverage or coverage measures.

Until approved, this section remains absent—not zero or “Low.”

## Status fields

| Field | Allowed values / meaning |
|---|---|
| `RiskStatus` | `READY`, `PENDING`, `BLOCKED` |
| `ValidationStatus` | `PASS`, `FAILED` |
| `ValidationReason` | Controlled reason codes plus human-readable explanation |
| `RiskLevel` | Optional derived controlled value after formula approval |
| `RiskWeightMultiplier` | Optional derived finite non-negative value after formula approval |

`READY` means required inputs exist and validate. It is not a recommendation,
not “low risk,” and not order approval.

# 4. Field Classification

Classification:

- A — required for the first production contract.
- B — optional when coverage exists; absence must be explicit.
- C — future extension requiring separate governance.
- D — not recommended for production risk assessment.

| Field | Class | Rationale |
|---|---|---|
| Ticker | A | Required identity |
| AsOfDate | A | Point-in-time boundary |
| RunId | A | Artifact consistency |
| ScoreModelVersion | A | Candidate provenance |
| RiskModelVersion | A | Formula provenance |
| PortfolioSnapshotId | A | Correlation/concentration context |
| PortfolioAsOfDate | A | Holdings freshness |
| CalculationTimestamp | A | Audit trail |
| ObservationEndDate | A | Leakage control |
| RiskObservationCount | A | Coverage validation |
| Volatility20D | A | Short-horizon market variability |
| Volatility60D | B | Longer context; requires sufficient history |
| TrailingDrawdown | A | Current price impairment from known history |
| ATR14 | B | Existing point-in-time range measure |
| AverageVolume20D | A | Basic capacity/liquidity context |
| AverageDollarVolume20D | A | Price-scaled liquidity context |
| LiquidityCoverage | A | Prevents sparse data appearing valid |
| Direct quoted bid-ask spread | C | Prefer when a reliable point-in-time source exists |
| OHLCV SpreadProxy | B | Approximate; must be labeled and validated |
| CurrentPortfolioWeight | A | Existing concentration input |
| CurrentSectorExposure | B | Requires governed sector taxonomy |
| CorrelationToPortfolio60D | B | Requires a non-empty portfolio and sufficient overlap |
| CorrelationObservationCount | B | Mandatory when correlation is present |
| ProposedSlotConcentration | B | Diagnostic based on configured slots, not a new rule |
| FundamentalRiskStatus | C | Requires structured source and governance |
| Leverage/coverage fundamentals | C | Valuable but reporting lag and units require separate design |

| ValidationStatus | A | Contract validity |
| ValidationReason | A | Auditability |
| RiskLevel | B | Only after explicit formula approval |
| RiskWeightMultiplier | B | Only after explicit formula approval |
| FinalScore | D in risk calculations | Candidate context only; high score must not neutralize risk |
| CandidateRank | D in risk calculations | Priority, not risk |
| BacktestScore | D | Strategy-research aggregate, not point-in-time risk |
| Legacy SharpeRatio | D | Derived from legacy strategy trades |
| Legacy MaxDrawdown | D | Derived from legacy strategy trades |
| Future forward returns | D | Direct leakage |
| Free-form Investment Profile text | D | Presentation context, not deterministic risk input |
| Analyst/LLM qualitative opinion | D | Non-reproducible unless separately governed and human-reviewed |

# 5. Data Source and Leakage Audit

| Field | Source | Calculation timing | Future leakage risk | Status |
|---|---|---|---|---|
| Ticker/RunId/AsOfDate/ScoreModelVersion | Validated production candidates | Copied after candidate validation | None if exact copy | A — required |
| RiskModelVersion | Risk calculator metadata | Assigned at calculation | None | A — required |
| PortfolioSnapshotId/PortfolioAsOfDate | Authoritative holdings/cash snapshot | Captured before assessment | Medium if later holdings are substituted | A — required; exact snapshot lock |
| ObservationEndDate | Canonical OHLCV cutoff | Set to latest used date | None if <= AsOfDate | A — required |
| Volatility20D/60D | Canonical Close history | Trailing window ending AsOfDate | High if centered/full-sample or future-filled | A/B; trailing-only tests required |
| TrailingDrawdown | Canonical Close history | Current Close versus prior rolling peak through AsOfDate | High if future peak or completed-trade path is used | A; explicitly trailing |
| ATR14 | Canonical OHLCV/indicator implementation | Window ending AsOfDate | Medium if latest runtime row exceeds candidate date | B; date isolation required |
| AverageVolume20D | Canonical Volume | Trailing 20 valid rows | Low if strictly truncated | A |
| AverageDollarVolume20D | Canonical Close × Volume | Trailing 20 valid rows | Low if strictly truncated | A |
| LiquidityCoverage | Same trailing window | At calculation | None | A |
| OHLCV SpreadProxy | Canonical High/Low/Close | Trailing window | Low leakage, high model/proxy error | B; label approximate |
| Direct bid-ask spread | Timestamped market quote source | At or before AsOfDate/time | High if end-of-day/future quote used | C; source timestamp required |
| CurrentPortfolioWeight | Holdings snapshot + current valuation | Before proposed order | Medium if post-trade/future positions used | A; pre-trade snapshot |
| CurrentSectorExposure | Holdings + governed security master | Before proposed order | Medium from stale taxonomy/holdings | B |
| CorrelationToPortfolio60D | Canonical histories + pre-trade holdings | Trailing overlap ending AsOfDate | High if future returns, survivor substitution, or proposed trade is included | B; isolation/coverage tests |
| ProposedSlotConcentration | Configured capital/slot assumptions | At assessment | None; scenario assumption risk | B; diagnostic only |
| Structured fundamental risk | Point-in-time filing/fundamental dataset | Latest known publication before AsOfDate | High from restated data or period-end/publication confusion | C; availability timestamp required |
| Investment Profile | Profile master data | Human context | No price leakage, but subjective/model-governance risk | D; presentation-only |
| Legacy Sharpe/MaxDrawdown | Legacy backtest trades | Full historical simulation | High mismatch; may include outcomes after candidate date | D; research-only |

Required leakage tests for a future calculator:

1. Mutating all rows after AsOfDate cannot change an earlier risk result.
2. ObservationEndDate never exceeds candidate AsOfDate.
3. Portfolio snapshot is pre-trade and immutable for the RunId.
4. Fundamental facts are gated by publication/availability date, not merely
   financial period end.
5. Missing observations remain missing; no backward fill from future data.

# 6. Legacy Risk Migration

| Legacy field | Classification | Migration |
|---|---|---|
| `BacktestScore` | A — remove from production; B — keep research | Replace production priority with FinalScore/CandidateRank; retain only in legacy reports |
| `SharpeRatio` | A — remove from production; B — keep research | Do not copy. If a new market-risk ratio is ever desired, define it independently using trailing point-in-time data |
| `MaxDrawdown` | A — remove from production; B — keep research; C — replace concept | Replace only with explicitly trailing `TrailingDrawdown`; do not reuse completed-trade strategy drawdown |
| `RiskLevel` | C — replace with new contract output | Retire legacy derivation; define controlled status/level only after new formula approval |
| Legacy `RiskScore`/`DrawdownScore` | A — remove; B — keep research | Never propagate into production risk contract |

The new contract does not claim that trailing volatility or drawdown predicts
future loss. Their role is to make current exposure and data uncertainty
observable, bounded, and auditable.

# 7. Fail-Closed Rules

| Condition | Decision | Required status/reason |
|---|---|---|
| Candidate not PortfolioEligible | BLOCK | `RiskStatus=BLOCKED`, `CANDIDATE_NOT_ELIGIBLE` or omit from calculator with audited count |
| All required risk data valid/current and contract passes | ALLOW to portfolio construction only | `RiskStatus=READY`, `ValidationStatus=PASS` |
| Required risk field missing | BLOCK | `RiskStatus=PENDING`, `REQUIRED_RISK_INPUT_MISSING` |
| Risk calculation exception/failure | BLOCK | `RiskStatus=BLOCKED`, `RISK_CALCULATION_FAILED` |
| NaN or infinity | BLOCK | `ValidationStatus=FAILED`, `NON_FINITE_RISK_VALUE` |
| Value outside approved range | BLOCK | `ValidationStatus=FAILED`, `RISK_VALUE_OUT_OF_RANGE` |
| Stale market data | BLOCK | `RiskStatus=PENDING`, `STALE_MARKET_DATA` |
| ObservationEndDate after AsOfDate | BLOCK | `ValidationStatus=FAILED`, `FUTURE_DATA_LEAKAGE` |
| Duplicate normalized Ticker | BLOCK entire artifact | `ValidationStatus=FAILED`, `DUPLICATE_TICKER` |
| Mixed candidate RunId | BLOCK entire artifact | `ValidationStatus=FAILED`, `MIXED_RUN_ID` |
| Candidate/risk RunId conflict | BLOCK affected join and pipeline | `ValidationStatus=FAILED`, `RUN_ID_MISMATCH` |
| Mixed AsOfDate or ScoreModelVersion | BLOCK entire artifact | `ValidationStatus=FAILED`, `MIXED_PROVENANCE` |
| RiskModelVersion missing/mixed | BLOCK entire artifact | `ValidationStatus=FAILED`, `RISK_MODEL_VERSION_INVALID` |
| Portfolio snapshot missing/stale/conflicting | BLOCK | `RiskStatus=PENDING/BLOCKED`, explicit snapshot reason |
| Insufficient volatility/drawdown history | BLOCK if field required | `RiskStatus=PENDING`, `INSUFFICIENT_HISTORY` |
| Correlation unavailable but optional | ALLOW only if approved base contract does not require it | `ValidationReason=OPTIONAL_CORRELATION_UNAVAILABLE` |
| Fundamental risk unavailable | ALLOW only while it is a future extension and not required | Explicitly absent; never default Low |
| Zero eligible candidates | ALLOW pipeline completion with no action | Stable empty risk/output schemas; `NO_ELIGIBLE_CANDIDATES` |
| All eligible candidates risk-pending/blocked | ALLOW pipeline completion with no positions/orders | `NO_RISK_READY_CANDIDATES` |

“ALLOW” means permission to proceed to the next internal construction step. It
never means BUY approval, order PASS, or investment recommendation.

# 8. Migration Plan

## Phase A — Risk contract approval

1. Approve the minimum A fields, units, windows, allowed ranges, coverage
   requirements, and freshness tolerance.
2. Decide whether any B field is required for V3.8.1 or deferred.
3. Approve controlled status/reason codes.
4. Define portfolio snapshot ownership and immutable RunId linkage.
5. Keep RiskLevel and multipliers disabled until their formula is separately
   approved.

Exit: signed contract specification and fixture examples; no runtime use.

## Phase B — Risk calculator creation

1. Implement an independent point-in-time calculator using canonical OHLCV and
   a supplied portfolio snapshot.
2. Add historical-date isolation and future-mutation tests.
3. Emit contract rows without connecting them to portfolio_risk.py.
4. Implement a separate strict validator and stable empty schema.

Exit: deterministic risk artifacts and passing leakage/validation tests.

## Phase C — Shadow validation

1. Join validated candidates and risk rows by Ticker/RunId/AsOfDate in a
   non-ordering shadow path.
2. Compare legacy RiskLevel outcomes only descriptively; do not tune the new
   contract to reproduce legacy classifications.
3. Exercise missing, stale, duplicate, non-finite, insufficient-history,
   zero-eligible, and all-pending scenarios.
4. Review coverage and operational failure rates across multiple dates.

Exit: human-approved evidence that the contract fails closed and remains
point-in-time safe.

## Phase D — Portfolio consumer migration

1. Make portfolio construction consume only candidate-eligible, risk-READY,
   validation-PASS rows.
2. Propagate all provenance and statuses.
3. Implement safe zero/all-pending behavior before weights are calculated.
4. Apply only approved portfolio caps and risk formulas.
5. Validate cash-only/no-order output for the current zero-eligible snapshot.

Exit: production portfolio has no dependency on legacy risk fields.

## Phase E — Legacy risk field removal

1. Remove BacktestScore, legacy SharpeRatio, MaxDrawdown, RiskScore,
   DrawdownScore, and legacy RiskLevel from production portfolio/order/report
   schemas and validators.
2. Remove legacy qualified-backtest path imports from production modules.
3. Retain legacy artifacts and calculations under research/backtest labeling.
4. Run repository-wide dependency search and full end-to-end validation.

Exit: legacy strategy metrics remain research evidence only.

# 9. Release Blockers

| Blocker | Severity | Required resolution |
|---|---|---|
| Minimum required risk fields/windows/ranges not approved | High | Phase A |
| Portfolio snapshot contract and provenance not defined | High | Phase A |
| No point-in-time risk calculator or leakage tests | High | Phase B |
| Active portfolio still derives risk from legacy Sharpe/MaxDrawdown | High | Phase D/E |
| RiskLevel/multiplier replacement formula unresolved | High before weighted construction | Separate approval before Phase D |
| All-pending/zero-risk candidates can currently produce NaN weights | High | Phase D |
| Missing/non-finite risk/order data can pass existing boundaries | Critical | Phase D and order migration |
| RunId/AsOfDate/model versions do not reach portfolio/orders/reports | High | Phase D |
| Current zero-eligible snapshot is not end-to-end no-action safe | High | Phase D |

Design conclusion: portfolio risk must measure current, understandable exposure
using only information available at the decision time. When the system cannot
establish that risk coherently, the correct state is cash and an explicit
BLOCK/PENDING result—not a guessed number, a legacy performance statistic, or
an automatic order.
