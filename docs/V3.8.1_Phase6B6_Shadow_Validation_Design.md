# AI_investing V3.8.1 Phase 6B-6 Shadow Validation Design

Design date: 2026-08-12

Status: design only. This document does not activate, migrate, or alter the
production portfolio pipeline.

# 1. Purpose and Non-Production Boundary

Phase 6B-6 defines a read-only shadow validation process for comparing the
validated production-candidate artifact with the independent point-in-time
risk artifact. Its purpose is to establish whether both contracts can be
joined reliably, whether required risk coverage is operationally adequate,
and whether failures remain visible and fail closed across multiple dates.

Shadow validation is evidence collection, not portfolio construction. It may
read copied or archived candidate and risk artifacts and produce diagnostic
tables or reports, but its results cannot approve a candidate, change a signal,
calculate a position, create an order, or feed an active production consumer.

The governing principle is that uncertainty is not equivalent to low risk.
Missing, stale, conflicting, or invalid risk evidence must be reported as
PENDING/BLOCKED or unmatched; it must never be zero-filled, inferred from the
candidate score, or treated as portfolio-ready.

Proposed non-production flow:

```text
validated_portfolio_candidates.csv ----+
                                        | strict diagnostic join
portfolio_risk_inputs.csv --------------+ on Ticker + RunId + AsOfDate
                                        |
                                        v
                              shadow validation metrics
                              and exception reports only
                                        |
                                        v
                               human governance review
```

# 2. Candidate Input Contract

Source: `results/validated_portfolio_candidates.csv`.

Row grain: one normalized Ticker within one RunId, AsOfDate, and
ScoreModelVersion candidate snapshot.

## Required candidate fields

| Field | Shadow use | Validation rule |
|---|---|---|
| `Ticker` | Identity and join key | Required, normalized, non-empty, unique within RunId/AsOfDate |
| `RunId` | Candidate-run provenance and join key | Required; one value per snapshot |
| `AsOfDate` | Point-in-time boundary and join key | Required valid ISO date; one value per snapshot |
| `ScoreModelVersion` | Score lineage | Required; one value per snapshot |
| `CandidateRank` | Diagnostic candidate ordering only | Required finite positive rank under the candidate contract |
| `FinalScore` | Candidate evidence only | Required finite value; never recalculated by shadow validation |
| `TradeSignal` | Preserved signal state | Required controlled value; never changed by shadow validation |
| `Eligibility` | Upstream candidate eligibility | Required controlled value |
| `PortfolioEligible` | Determines expected risk-row population | Required Boolean; never promoted by shadow validation |
| `ValidationStatus` | Candidate adapter result | Required controlled status |
| `ValidationReason` | Candidate rejection explanation | Required field; may be empty only when permitted by its status |

Candidate-side preconditions:

1. Identity and metadata cannot be null or mixed inside a snapshot.
2. Duplicate normalized tickers invalidate that snapshot.
3. Only `PortfolioEligible=True` rows are expected to have risk rows under the
   approved Phase 6B-5 calculator contract.
4. WATCH, IGNORE, and other non-eligible rows remain part of candidate coverage
   accounting but must not become risk-ready through the join.
5. FinalScore, TradeSignal, Eligibility, and PortfolioEligible are immutable
   source evidence.

# 3. Risk Input Contract

Source: `results/portfolio_risk_inputs.csv`.

Row grain: one assessed PortfolioEligible Ticker for one candidate RunId,
AsOfDate, portfolio snapshot, and RiskModelVersion.

## Required risk fields

| Field | Shadow use | Validation rule |
|---|---|---|
| `Ticker` | Identity and join key | Required, normalized, non-empty, unique within RunId/AsOfDate |
| `RunId` | Risk-run provenance and join key | Required and equal to candidate RunId |
| `AsOfDate` | Risk cutoff and join key | Required and equal to candidate AsOfDate |
| `ScoreModelVersion` | Candidate lineage carried into risk | Required and equal to the matched candidate value |
| `RiskModelVersion` | Risk-model lineage | Required deterministic approved value; one value per snapshot |
| `PortfolioSnapshotId` | Pre-trade portfolio provenance | Required for READY/PASS rows |
| `PortfolioAsOfDate` | Portfolio-state cutoff | Required for READY/PASS; must be no later than AsOfDate |
| `CalculationTimestamp` | Operational audit timestamp | Required for assessed rows; not a market-data cutoff |
| `ObservationEndDate` | Last market observation used | Required for READY/PASS; must be no later than AsOfDate |
| `RiskObservationCount` | History coverage | Required finite count for READY/PASS |
| `Volatility20D` | Trailing point-in-time risk input | Required finite value for READY/PASS |
| `Volatility60D` | Approved longer-horizon context | Finite when emitted; absence handled per approved contract |
| `TrailingDrawdown` | Current drawdown from known trailing peak | Required finite value for READY/PASS |
| `ATR14` | Approved range context | Finite when emitted; absence handled per approved contract |
| `AverageVolume20D` | Trailing share-liquidity input | Required finite value for READY/PASS |
| `AverageDollarVolume20D` | Trailing dollar-liquidity input | Required finite value for READY/PASS |
| `LiquidityCoverage` | Supporting-observation completeness | Required finite value for READY/PASS |
| `CurrentPortfolioWeight` | Pre-trade ticker exposure | Required finite value in the approved range for READY/PASS |
| `RiskStatus` | Readiness state | Controlled value: `READY`, `PENDING`, or `BLOCKED` |
| `RiskValidationStatus` | Contract validation state | Controlled value: `PASS` or `FAILED` |
| `RiskValidationReason` | Explicit failure explanation | Required field; non-empty for non-PASS rows |

Only `RiskStatus=READY` together with `RiskValidationStatus=PASS` is counted as
risk-ready. This designation remains diagnostic and does not authorize
portfolio construction or an order.

Legacy BacktestScore, legacy trade SharpeRatio, completed-trade MaxDrawdown,
future returns, and fabricated RiskLevel are forbidden from the shadow
contract.

# 4. Strict Join Contract

The sole approved join key is the exact composite key:

```text
Ticker + RunId + AsOfDate
```

No fallback join is permitted. In particular, the shadow process must not join
on Ticker alone, use nearest dates, substitute the latest RunId, forward-fill a
risk row, or reuse a prior portfolio snapshot.

Before joining:

1. Normalize Ticker under the same candidate/risk convention.
2. Parse AsOfDate to a canonical date representation without changing its
   economic date.
3. Require non-null values for all three keys.
4. Require key uniqueness independently in each artifact.
5. Reject mixed RunId, mixed AsOfDate, or mixed model-version snapshots rather
   than selecting an arbitrary value.

The diagnostic join must be a full outer join so unmatched rows remain
observable. Each resulting row receives one join classification:

| Join status | Definition | Governance outcome |
|---|---|---|
| `MATCHED` | Exact key exists once in both artifacts | Continue contract checks |
| `CANDIDATE_ONLY_EXPECTED` | Candidate is not PortfolioEligible and no risk row exists | Valid no-risk-required state |
| `CANDIDATE_ONLY_MISSING_RISK` | Candidate is PortfolioEligible but no risk row exists | Coverage failure; fail closed |
| `RISK_ONLY_ORPHAN` | Risk row has no exact candidate key | Provenance failure; fail closed |
| `DUPLICATE_KEY` | Either artifact has repeated composite key | Snapshot invalid; fail closed |

ScoreModelVersion must agree after an exact-key match. RiskModelVersion and
portfolio-snapshot metadata are validated as risk provenance, not appended to
the join key.

# 5. Coverage Metrics

Coverage must be reported for every RunId/AsOfDate snapshot and for the full
multi-date validation set. Counts and denominators must be shown together; a
percentage without its denominator is insufficient.

## Candidate population metrics

- total candidate rows;
- candidate-valid rows;
- PortfolioEligible rows;
- non-eligible rows;
- distinct candidate tickers; and
- duplicate/invalid candidate rows.

## Join coverage metrics

- expected risk rows = count of PortfolioEligible candidate rows;
- matched eligible rows;
- eligible candidate rows missing risk;
- risk-only orphan rows;
- exact-match coverage = matched eligible rows / expected risk rows;
- provenance-valid matches; and
- provenance-valid coverage = provenance-valid matches / expected risk rows.

When expected risk rows equal zero, coverage is reported as `N/A`, accompanied
by `NO_ELIGIBLE_CANDIDATES`; it must not be presented as an artificial 100%.

## Risk readiness metrics

- READY/PASS rows;
- PENDING/FAILED rows;
- BLOCKED/FAILED rows;
- invalid status combinations;
- risk-ready coverage = READY/PASS rows / expected risk rows; and
- finite-field coverage for each required numeric risk field.

No target percentage is approved in this design. Shadow validation reports
observed coverage; it does not tune validation rules to improve it.

# 6. Risk Status Distribution

For each RunId/AsOfDate and for the complete study, report a cross-tabulation of
`RiskStatus` by `RiskValidationStatus`, including counts and percentages of
expected risk rows.

At minimum, distinguish:

- `READY/PASS`;
- `PENDING/FAILED`;
- `BLOCKED/FAILED`;
- missing risk status;
- unknown status values; and
- inconsistent combinations such as READY/FAILED or PENDING/PASS.

Unknown or inconsistent status combinations are validation failures, not an
“other ready” category. Non-eligible candidates are reported separately and do
not dilute the expected-risk denominator.

# 7. Failure Reason Reporting

Every non-PASS matched risk row and every unmatched/invalid row must have an
auditable reason. Reporting includes:

- standardized reason code or normalized reason category;
- original reason text without silent rewriting;
- count and percentage by RunId/AsOfDate;
- affected distinct tickers;
- first and last observed dates in the validation set; and
- representative composite keys for investigation.

Required categories include, when observed:

- missing portfolio snapshot;
- stale portfolio snapshot;
- insufficient market history;
- stale market data;
- non-finite or out-of-range risk value;
- risk calculation failure;
- candidate/risk provenance conflict;
- missing eligible risk row;
- orphan risk row;
- duplicate composite key;
- future-dated observation or portfolio state; and
- unknown or missing status/reason.

Failure rows must not be dropped from summary denominators. Empty reasons on a
FAILED row are themselves reported as `MISSING_FAILURE_REASON`. Reports must
not disclose guessed risk values or convert operational absence into zero.

# 8. Multi-Date Validation Requirements

A single current snapshot, especially a zero-eligible snapshot, cannot establish
operational coverage. Shadow validation must use immutable archived artifact
pairs spanning multiple AsOfDates and RunIds.

The validation set must include, at minimum:

1. a date with zero PortfolioEligible candidates;
2. a date with one eligible candidate;
3. a date with multiple eligible candidates;
4. a date with sufficient, current market history;
5. a date with insufficient history;
6. a stale-market-data case;
7. a missing or conflicting portfolio-snapshot case;
8. a PENDING and a BLOCKED outcome;
9. a normal READY/PASS outcome; and
10. an intentionally malformed copy testing duplicate and provenance failure.

Use several market regimes when archived evidence permits, but do not use
future performance to select dates or judge the risk model. For each date,
store or record artifact identity, hashes where available, row counts, model
versions, calculation timestamp, test-fixture status, and validation outcome.

Historical reconstruction must preserve the candidate universe and portfolio
state actually known at that date. Substituting today's universe, holdings, or
metadata is not point-in-time validation and must be labeled invalid rather
than approximated.

# 9. Point-in-Time Leakage Validation

Shadow validation must repeat and extend the Phase 6B-5 leakage controls:

1. For a candidate at date D, mutate every OHLCV value after D, including
   extreme and non-finite values; the result at D must remain identical.
2. Append future OHLCV rows; the result at D must remain identical.
3. Verify `ObservationEndDate <= AsOfDate` for every READY/PASS row.
4. Verify `PortfolioAsOfDate <= AsOfDate` and that the portfolio snapshot is
   pre-trade and immutable for its RunId.
5. Verify no forward returns, completed future trade outcomes, future universe
   membership, or later portfolio holdings enter either artifact.
6. Verify no backward fill or nearest-date join imports future information.
7. Re-run an archived input pair and compare all deterministic risk fields;
   CalculationTimestamp may differ and must not be used as a market cutoff.
8. Treat any leakage invariant violation as snapshot failure, regardless of
   otherwise favorable risk values or coverage.

Leakage evidence must be reported per date and in aggregate. A passing current
snapshot cannot offset a leakage failure on another date.

# 10. Explicit Production Boundary

Phase 6B-6 authorizes design and future diagnostic shadow outputs only. It does
not authorize any production consumer change.

Explicitly prohibited in shadow validation:

- no migration or modification of `portfolio_risk.py`;
- no switch from the legacy production portfolio input path;
- no position-sizing changes;
- no portfolio weights, allocations, or proposed shares;
- no order draft, order review, brokerage instruction, or order generation;
- no daily decision report behavior change;
- no trading-signal, BUY/WATCH threshold, FinalScore, or eligibility change;
- no RiskLevel or risk multiplier fabrication;
- no optimization or parameter selection from observed coverage; and
- no shadow result consumed as production authorization.

The shadow validator must remain physically and logically downstream of both
source artifacts and outside the active execution path. Its outputs are marked
`SHADOW`, read-only for governance review, and fail closed when provenance or
risk evidence is unclear.

# 11. Proposed Shadow Outputs

Future implementation may create research-only artifacts such as:

- `results/shadow_candidate_risk_join.csv` — row-level full-outer-join audit;
- `results/shadow_validation_coverage.csv` — per-date and aggregate coverage;
- `results/shadow_risk_status_distribution.csv` — status cross-tabulation;
- `results/shadow_failure_reasons.csv` — normalized failure inventory; and
- a Phase 6B-6 execution report.

These names are design proposals, not implemented files. Generated artifacts
must remain outside production consumption and carry explicit shadow labeling.

# 12. Exit Criteria and Remaining Governance

Shadow validation is complete only when:

1. every input snapshot passes schema, uniqueness, and provenance validation;
2. join coverage and risk-ready coverage are reported with denominators;
3. all unmatched, failed, pending, blocked, unknown, and inconsistent rows are
   retained and explained;
4. the required multi-date scenarios are exercised;
5. all leakage tests pass independently for every applicable date;
6. zero-eligible and all-not-ready snapshots produce safe no-action evidence;
7. no shadow output enters production portfolio or order consumers; and
8. human governance review accepts the evidence.

Passing shadow validation is necessary but not sufficient for portfolio
migration. Consumer migration requires a separately approved implementation
phase, explicit portfolio safety tests, and removal of legacy dependencies only
after the new path has demonstrated fail-closed behavior.

Design conclusion: shadow validation should make missing knowledge visible. It
must never turn incomplete risk evidence into a position merely because a
candidate has a strong score or BUY signal. When the contracts cannot establish
risk coherently, the correct diagnostic outcome is no action and explicit human
review.
