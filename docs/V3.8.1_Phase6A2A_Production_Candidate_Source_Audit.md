# AI_investing V3.8.1 Phase 6A-2A Production Candidate Source Audit

Audit date: 2026-08-12

Scope: architecture audit only. No production code, scoring logic, threshold,
portfolio rule, order rule, or backtest behavior was changed.

## 1. Current Architecture

### Production scoring and reporting path

```text
data/<Ticker>.csv
  -> stock_loader.load_stock()
  -> indicators.calculate_indicators()
  -> rank_stocks_v2.process_single_stock()
  -> score.calculate_rank_score_diagnostics()
  -> score.calculate_final_score()
  -> trade_signal.generate_signals()
  -> rank_stocks_v2.rank_stocks()
  -> results/stock_rank.csv + results/top10.csv
  -> daily technical report / stock-card top-opportunity display
```

This path uses current RawScore, RS_Score, NearHighScore, FinalScore, and
TradeSignal. BUY and WATCH states are generated here. It does **not** feed the
model portfolio pipeline.

### Actual portfolio candidate and order path

```text
data/<Ticker>.csv
  -> backtest_engine.prepare_backtest_data()
  -> backtest_engine.generate_historical_trade_signals()
  -> non-BUY -> BUY entry transitions
  -> fixed-holding performance summaries
  -> backtest_engine.backtest_watchlist()
  -> IsQualified + BacktestScore
  -> results/backtest_qualified_20d.csv
  -> portfolio_risk.load_qualified_candidates()
  -> portfolio_risk.build_model_portfolio()
  -> results/model_portfolio.csv
  -> combined_scoring.calculate_combined_score()
  -> results/combined_score.csv
  -> position_sizing.load_model_portfolio()
  -> results/model_portfolio_sizing.csv
  -> order_draft.build_order_draft()
  -> results/order_draft.csv
  -> order_review.build_order_review()
  -> results/order_review.csv
  -> portfolio_action_report.build_action_report_text()
  -> daily_decision_report.build_daily_decision_report()
```

`run_portfolio.main()` begins by calling
`portfolio_risk.print_model_portfolio()`. It does not run current ranking or a
backtest first; it consumes whichever `results/backtest_qualified_20d.csv`
already exists.

### Candidate source identification

| Question | Finding |
|---|---|
| Current technical candidates created by | `rank_stocks_v2.rank_stocks()` |
| Current technical candidate artifacts | `results/stock_rank.csv`, `results/top10.csv` |
| Portfolio candidates created by | `backtest_engine.backtest_watchlist()` |
| Portfolio candidate artifact | `results/backtest_qualified_20d.csv` |
| Portfolio candidate consumer | `portfolio_risk.load_qualified_candidates()` |
| Portfolio selection function | `portfolio_risk.build_model_portfolio()` |
| Portfolio ranking field | `BacktestScore` descending |
| Uses current FinalScore | Technical ranking: YES; portfolio selection: NO |
| Uses current TradeSignal | Technical ranking: YES; portfolio selection: NO |
| Uses current BUY/WATCH state | Technical reports: YES; portfolio selection: NO |
| Uses backtest qualification | Portfolio selection: YES |
| Uses legacy technical filters | Portfolio qualification: YES |

The current portfolio pipeline therefore has no same-day candidate-selection
step based on production BUY or WATCH state.

## 2. Legacy Dependency Findings

### Production-path dependencies

| Module | Dependency | Role |
|---|---|---|
| `config.py` | `BACKTEST_QUALIFIED_20D_OUTPUT_PATH` | Defines active portfolio candidate file |
| `backtest_engine.py` | Technical-filter BUY, entry transitions, fixed-holding results, qualification, BacktestScore | Creates candidate source |
| `run_backtest.py` | `backtest_watchlist(holding_days=20)` | Runs legacy candidate generation |
| `validate_backtest_outputs.py` | Qualified legacy CSV contract | Validates the candidate artifact |
| `portfolio_risk.py` | `results/backtest_qualified_20d.csv` | Loads and ranks active portfolio candidates |
| `validate_portfolio_outputs.py` | Legacy performance and BacktestScore columns | Validates model portfolio |
| `combined_scoring.py` | Requires `BacktestScore`; gives it 70% combined-score weight | Propagates legacy score downstream |
| `validate_combined_outputs.py` | Validates BacktestScore and weighted formula | Enforces legacy-shaped contract |
| `position_sizing.py` | Converts and falls back to `BacktestScore` | Propagates legacy score into sizing |
| `validate_position_sizing_outputs.py` | Requires `BacktestScore` | Enforces downstream contract |
| `order_draft.py` | Requires/copies `BacktestScore` | Propagates it into draft orders |
| `validate_order_draft_outputs.py` | Requires `BacktestScore` | Enforces order schema |
| `order_review.py` | Requires/copies `BacktestScore` | Propagates it into reviewed orders |
| `validate_order_review_outputs.py` | Requires `BacktestScore` | Enforces reviewed-order schema |
| `portfolio_action_report.py` | Displays `BacktestScore` | Presents legacy result to user |
| `report_terminal.py` / stock cards | Read model portfolio and combined-score artifacts | Indirectly display legacy-derived candidates |
| `daily_decision_report.py` | Embeds portfolio action report | Indirect terminal consumer |

The legacy `generate_historical_trade_signals()` BUY rule uses Close > MA20,
MA20 > MA60, Volume_Ratio > 0.8, and DistanceToHigh >= 0.95. It does not
calculate or require production FinalScore >= 75. Legacy WATCH means required
technical fields are present, not production FinalScore >= 60.

Legacy qualification requires at least 10 completed trades, positive average
return, win rate of at least 50%, and no processing error. BacktestScore is a
weighted aggregate of average return, win rate, trade count, worst trade, and
drawdown. It is not production FinalScore.

### Research-only dependencies

| Module | Input/purpose | Production-path status |
|---|---|---|
| `production_backtest.py` | Reconstructs current production FinalScore and TradeSignal historically | Research-only |
| `trade_event_backtest.py` | Consumes production signal history and creates BUY entry events | Research-only |

| `portfolio_robustness.py` | Benchmark/execution/cost/contribution diagnostics | Research-only |

No call or import connects `production_backtest.py` to `portfolio_risk.py` or
`run_portfolio.py`.

## 3. Data Contract Comparison

Current artifacts were inspected directly. The legacy qualified file contains
10 rows and 21 columns; the existing production-faithful signal file contains
680 historical BUY/WATCH observations and 13 columns. The latter artifact was
generated before Phase 6A-1 and still displays the retired RiskScore values, so
it must be regenerated before any future integration assessment.

| Contract area | Legacy `backtest_qualified_20d.csv` | Production-faithful `production_backtest_signals.csv` |
|---|---|---|
| Row unit | One qualified ticker summary | One ticker/signal-date observation |
| Ticker | `Ticker` | `Ticker` |
| Date | No signal/as-of date | `SignalDate` |
| Production score | None | `FinalScore` |
| Component scores | None | `TrendScore`, `MomentumScore`, `RSScore`, `NearHighScore`, `VolumeScore`, `RiskScore` |
| Signal | No production signal | `TradeSignal` (`BUY` or `WATCH`) |
| Current ranking | None | No explicit Rank; can only be derived per date |
| Legacy qualification | `IsQualified` | None |
| Legacy performance | `AverageReturn`, `WinRate`, `BestTrade`, `WorstTrade`, `TotalReturn`, `CAGR`, `MaxDrawdown`, `SharpeRatio` | Forward 5D/20D/60D returns per observation only |
| Legacy activity | `BuySignalDays`, `EntrySignalCount`, `CompletedTradeCount`, `TotalRows` | None |
| Legacy score | `AverageReturnScore`, `WinRateScore`, `TradeCountScore`, `RiskScore`, `DrawdownScore`, `BacktestScore` | None |
| Error state | `Error` | None |
| Portfolio RiskLevel inputs | `MaxDrawdown`, `SharpeRatio` | Missing |
| Fundamental fields | None | None |
| Price for sizing | None; sizing reads latest canonical Close separately | No Close field |
| Model metadata | None | Current schema has no ScoreModelVersion |
| Forward evaluation | Aggregated fixed-holding trade metrics | `Forward5DReturn`, `Forward20DReturn`, `Forward60DReturn` |

The two `RiskScore` names are semantically unrelated: the legacy file's value
is a performance-derived worst-trade subscore, whereas the production signal
field is the technical model diagnostic field.

### Fields required by the immediate portfolio consumer

`portfolio_risk.build_model_portfolio()` directly requires:

- `Ticker`;
- `BacktestScore`, for sorting;
- `MaxDrawdown` and `SharpeRatio`, for RiskLevel assignment; and
- the remaining legacy performance columns indirectly because
  `validate_portfolio_outputs.py` requires `AverageReturn` and `WinRate` and the
  resulting artifact/report displays them.

The production-faithful signal output provides only `Ticker` from that set.

### Fields required farther downstream

The existing chain also assumes:

- `BacktestScore` in combined scoring, position sizing, draft orders, reviewed
  orders, action reports, and validators;
- portfolio-created `RiskLevel`, `RiskWeightMultiplier`, `TargetWeight`,
  `TargetWeightPercent`, and `PortfolioRole`;
- fundamental merge fields `FundamentalScore`, `CombinedScore`, and
  `FundamentalRating`;
- sizing fields including `LatestClose`, `TargetDollarAmount`, and
  `TargetShares`; and
- order/review status fields.

## 4. Replacement Feasibility

**FAIL — the production-faithful signal CSV cannot directly replace the legacy
candidate source.**

Reasons:

1. Its row grain is historical signal observation, not one current candidate
   per ticker. Direct loading would include stale dates and duplicate tickers.
2. It includes WATCH observations; the existing portfolio pipeline has no
   contract deciding whether only current BUY or BUY plus WATCH is eligible.
3. It lacks `BacktestScore`, the active sort and combined-score input.
4. It lacks `MaxDrawdown` and `SharpeRatio`, which currently determine
   RiskLevel and risk multipliers.
5. It lacks legacy validation fields required by the existing model-portfolio
   validator and reports.
6. It lacks an explicit current-date selection/ranking contract and currently
   has no AsOfDate/RunId compatibility enforcement.
7. The current artifact predates the Phase 6A-1 score correction and must not
   be treated as current merely because its filename matches the new path.

A direct column rename such as `FinalScore -> BacktestScore` would be
semantically false. Likewise, deriving RiskLevel from production component
RiskScore would be invalid because it is not the legacy drawdown/Sharpe risk
contract.

## 5. Recommended Implementation Plan

1. Define a new, versioned **current production candidate contract** rather
   than pointing `portfolio_risk.py` at a historical research CSV. Its row unit
   should be one ticker for one explicit AsOfDate/RunId.
2. Source that contract from the current ranking output after production
   `generate_signals()`, with an explicit eligibility decision made under
   separate approval (for example, whether candidates must be current BUY).
   Do not infer or change this policy during migration.
3. Include at minimum `Ticker`, `AsOfDate`, `FinalScore`, `TradeSignal`,
   `ScoreModelVersion`, and deterministic rank/tie-breaking metadata.
4. Separate candidate ranking from historical validation. Retain production-
   faithful performance evidence as attached research metadata where needed,
   but do not rename it into FinalScore or make legacy technical qualification
   the production eligibility gate.
5. Define a replacement RiskLevel contract. The current production-faithful
   signal CSV cannot supply legacy MaxDrawdown/Sharpe inputs, and Phase 6A-2A
   does not authorize inventing a new risk rule.
6. Adapt combined scoring and downstream schemas deliberately. If FinalScore
   replaces BacktestScore, update names, formulas, validators, reports, and
   tests together; do not use a compatibility alias that hides changed
   semantics.
7. Add explicit empty, duplicate-ticker, stale-date, mixed-version, missing-
   field, and non-finite-value rejection before connecting the new contract to
   portfolio construction.
8. Preserve the legacy backtest as a clearly labeled research tool, remove it
   from production candidate eligibility, and update module documentation to
   prevent claims that it validates production BUY.
9. Complete the migration in a separately approved implementation phase with
   old/new artifact comparison and full portfolio/order/report regression
   validation.

No replacement is implemented by this audit.
