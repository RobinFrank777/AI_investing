## Root Cause

This is Decision Tree Case C: the provider repeatedly returned internally
invalid completed-session rows. The local lifecycle defect was accepting those
rows without applying the canonical OHLCV invariant before publication.

The issue is not intraday partial-bar lifecycle, adjustment mixing, a split,
dividend, symbol event, or local merge corruption.

## Fix

`update_data.py` now:

1. normalizes the downloaded frame into the single unadjusted OHLCV domain;
2. validates finite positive O/H/L/C, non-negative Volume, High bounds, and Low
   bounds before publication;
3. rejects invalid refreshed rows;
4. combines only whole valid canonical rows;
5. replaces a same-date valid row atomically, never column-by-column;
6. retains a prior same-date row only if that entire prior row is valid;
7. removes a previously polluted invalid row through the same generic contract;
8. publishes through a temporary file followed by atomic replace;
9. returns `provider_rejected` with rejected dates and the latest retained valid
   date.

`data_readiness.py` now explicitly marks otherwise-valid symbols behind the
universe latest date as `STALE_MARKET_DATA`, preventing a misleading 148-ready
claim.

No ticker-specific rule was added. The five production files were remediated by
the official generic updater, not hand edited.

## Canonical Atomic-Row Contract

- Atomic replacement: YES. A Date/OHLCV row is the minimum update unit.
- Same-date valid refresh: the entire refreshed row wins deterministically.
- Column-wise mixed row: prohibited and tested.
- Duplicate dates: stable sort, keep the last complete valid refresh row.
- Invalid refresh: rejected before canonical publication.
- Existing valid row preservation: YES, as a whole row.
- Existing invalid row preservation: NO.
- Current AsOf fabrication after rejection: NO.
