# AI_investing V3.8.1 Phase 6B-8B Historical Shadow Validator Report

Date: 2026-08-12

Status: independent research/archive validation only. No production portfolio,
sizing, signal, risk calculation, or order consumer is connected to this
validator.

# 1. Purpose

`historical_shadow_validator.py` implements the Phase 6B-8A fail-closed
contract for an existing `archive/shadow/YYYY-MM-DD/` record. It validates
archive structure, content hashes, cross-file metadata, candidate/risk
contracts, eligible-candidate risk coverage, scenario classification, and
cross-archive immutability.

The validator reads captured artifacts without recalculating FinalScore,
TradeSignal, CandidateRank, Eligibility, or risk values. A PASS means the
archive contract is internally valid. It never means a security, portfolio,
position size, order, or trade is approved.

# 2. Implemented Archive Contract

Each validated directory must contain:

```text
candidates.csv
risk.csv
portfolio_snapshot.json
manifest.json
validation_report.md
```

The manifest must list exactly those five contract files and contain:

- RunId;
- AsOfDate;
- ScoreModelVersion;
- RiskModelVersion;
- PortfolioSnapshotId;
- CandidateArtifactHash;
- RiskArtifactHash;
- PortfolioSnapshotHash; and
- ValidationReportHash.

The four non-manifest content hashes must be valid SHA-256 digests and match
the file bytes. The manifest is not self-hashed, avoiding an impossible
circular digest.

# 3. Validation Boundaries

## Archive and hash validation

- missing archive or required file -> `ARCHIVE_FILE_MISSING`;
- unreadable/incomplete manifest -> `INVALID_MANIFEST`; and
- changed file bytes -> `ARCHIVE_HASH_MISMATCH`.

## Metadata validation

The manifest is authoritative for the captured archive identity. The validator
requires consistent metadata across the sources where each field is defined:

| Field | Compared sources |
|---|---|
| RunId | manifest, candidate rows, risk rows, portfolio snapshot, validation report |
| AsOfDate | manifest/directory, candidate AsOfDate, risk RiskAsOfDate, portfolio snapshot, validation report |
| ScoreModelVersion | manifest, candidate rows, risk rows, portfolio snapshot, validation report |
| RiskModelVersion | manifest, risk rows, portfolio snapshot, validation report |
| PortfolioSnapshotId | manifest, risk rows, portfolio snapshot, validation report |

Any missing, mixed, or conflicting value produces `METADATA_MISMATCH`.
Header-only candidate/risk files are supported; their identity remains
mandatory in the manifest, portfolio snapshot, and validation report.

## Candidate validation

Required fields are Ticker, FinalScore, TradeSignal, CandidateRank,
Eligibility, RunId, AsOfDate, and ScoreModelVersion.

The validator rejects missing fields, missing/duplicate normalized Ticker,
missing RunId, NaN/infinite FinalScore, and ELIGIBLE promotion of a non-BUY row
with `INVALID_CANDIDATE_ARCHIVE`.

It preserves archived candidate values and does not rerank or repair them.

## Risk validation

Required risk fields are Ticker, RiskStatus, RiskModelVersion, RiskAsOfDate,
PortfolioSnapshotId, RunId, and ScoreModelVersion.

Allowed RiskStatus values are exactly:

- READY;
- PENDING;
- BLOCKED; and
- FAILED.

UNKNOWN, PASS, BUY, empty values, and other states produce
`INVALID_RISK_ARCHIVE`. Duplicate/missing risk tickers are also rejected.

# 4. Candidate-Risk Coverage

Every candidate with Eligibility=ELIGIBLE must have one risk row with the same
normalized Ticker. Global RunId, date, model, and portfolio identity must
already have passed metadata validation.

An uncovered eligible candidate produces `MISSING_RISK`; the validator does
not fabricate a pending or zero-risk row.

Non-eligible candidates do not require a risk row. This permits the real
zero-eligible/header-only risk scenario without inventing evidence.

# 5. Scenario Detection

After the archive passes structural validation, the validator emits one
deterministic scenario:

| Scenario | Rule |
|---|---|
| `ZERO_ELIGIBLE` | No ELIGIBLE candidate |
| `SINGLE_ELIGIBLE` | Exactly one ELIGIBLE candidate and no BLOCKED/FAILED risk row |
| `MULTIPLE_ELIGIBLE` | More than one ELIGIBLE candidate and no BLOCKED/FAILED risk row |
| `RISK_BLOCKED` | At least one BLOCKED or FAILED risk row |

PENDING is counted separately and does not become READY. A structurally valid
PENDING archive may PASS archive validation, while remaining non-actionable.
RISK_BLOCKED takes precedence because the archive must make adverse evidence
prominent.

# 6. Immutability Validation

`validate_archive_immutability()` scans manifest files under an archive root.
For each RunId + AsOfDate identity it compares CandidateArtifactHash and
RiskArtifactHash.

Two records with the same identity and different artifact hashes produce:

`IMMUTABILITY_VIOLATION`

Identical repeated fingerprints do not create a false violation, although the
Phase 6B-8A archive publisher remains responsible for refusing an existing
canonical AsOfDate directory. The validator never modifies an archive.

# 7. Output Contract

`validate_and_write()` generates:

`results/shadow_validation_report.json`

with the stable fields:

```json
{
  "RunId": "",
  "AsOfDate": "",
  "candidate_count": 0,
  "eligible_count": 0,
  "risk_ready": 0,
  "risk_pending": 0,
  "risk_blocked": 0,
  "scenario": "ZERO_ELIGIBLE",
  "status": "PASS"
}
```

`risk_blocked` combines BLOCKED and FAILED rows. The additional scenario field
is required for the requested automatic scenario detection. No position,
sizing, holdings, order, target, or production-action field is emitted.

On validation failure, the validator raises
`HistoricalShadowValidationError` with a stable code and does not write a PASS
report.

# 8. Tests

The dedicated suite contains 13 tests covering:

1. valid archive PASS and JSON output;
2. missing manifest;
3. hash mismatch;
4. metadata mismatch;
5. duplicate normalized ticker;
6. missing risk for an eligible candidate;
7. invalid RiskStatus;
8. zero eligible scenario;
9. single eligible scenario;
10. multiple eligible scenario;
11. blocked/failed risk scenario and count;
12. immutability violation; and
13. archive input immutability.

Final repository-wide tests, syntax compilation, and diff validation are
reported in the Phase 6B-8B handoff.

# 9. Production Boundary Confirmation

The implementation creates only:

- `historical_shadow_validator.py`;
- `tests/test_historical_shadow_validator.py`; and
- this report.

It does not import, call, or modify portfolio construction, position sizing,
order draft/review, daily decision reporting, score, signal, candidate builder,
candidate adapter, or risk calculation behavior. The default output remains
under ignored `results/` and is research evidence only.

# 10. Remaining Work

This phase validates existing archive directories; it does not publish them.
A separately approved writer is still required to perform atomic creation,
refuse overwrite, canonicalize bytes, and capture real historical evidence.

No real archive was created in Phase 6B-8B. Therefore the Phase 6B-7 evidence
gaps remain open until unbiased, immutable, multi-date records exist.
