# 1. Objective

Phase 6B-8E2 implements the Phase 6B-8E1 portfolio snapshot provenance
contract as an independent builder. The module binds one validated candidate
artifact, one risk artifact, and one explicitly supplied authoritative
portfolio state into a deterministic, immutable JSON provenance object.

The builder creates identity and evidence custody only. It does not obtain
brokerage data, infer holdings, calculate candidates or risk, create positions,
select weights, or authorize an investment action.

# 3. Builder Contract

Primary interface:

```text
PortfolioSnapshotBuilder.build_snapshot(
    candidate_path,
    risk_path,
    portfolio_state,
    run_id=...,
    as_of_date=...,
    portfolio_as_of_date=...,
    portfolio_source_id=...,
    base_currency=...,
    evidence_classification=...,
    captured_timestamp=...,
) -> dict
```

Immutable publication interface:

```text
PortfolioSnapshotBuilder.publish_snapshot(snapshot, output_path) -> Path
```

The builder requires explicit inputs. It has no default production paths, no
broker connection, and no production pipeline entry point.

# 4. Deterministic Identity

The canonical state contains:

- PortfolioSnapshotContractVersion;
- PortfolioAsOfDate;
- PortfolioSourceId;
- BaseCurrency;
- ValuationConventionVersion;
- normalized and sorted holdings;
- normalized and sorted cash balances;
- exact decimal TotalPortfolioValue;
- SourceStatus; and
- ReconciliationStatus.

Canonical state JSON uses UTF-8, sorted keys, fixed separators, and a terminal
newline. SHA-256 of those bytes becomes `PortfolioStateHash`.

`PortfolioSnapshotId` is derived as:

```text
portfolio-snapshot-{PortfolioAsOfDate YYYYMMDD}-{first 12 hash characters}
```

RunId, candidate/risk hashes, CapturedTimestamp, and later risk outcomes are
excluded from state identity, preventing circular or operationally unstable
IDs. Changing holdings, cash, valuation, source context, or reconciliation
state changes the state hash and ID.

# 5. Artifact Binding

The builder reads candidate and risk files as immutable evidence and calculates
SHA-256 from their exact bytes.

Candidate validation requires:

- Ticker, RunId, AsOfDate, ScoreModelVersion, and PortfolioEligible columns;
- at least one provenance row;
- one non-empty RunId, AsOfDate, and ScoreModelVersion;
- exact caller RunId/AsOfDate match;
- unique, non-empty normalized tickers; and
- controlled Boolean PortfolioEligible values.

The snapshot records CandidateArtifactHash, CandidateRowCount, and
PortfolioEligibleCount.

Risk validation requires a stable schema even for a header-only zero-risk
artifact. Populated rows must have one exact:

- RunId;
- AsOfDate;
- ScoreModelVersion;
- RiskModelVersion;
- PortfolioSnapshotId; and
- PortfolioAsOfDate.

Any conflict produces `RISK_SNAPSHOT_MISMATCH`. The exact risk bytes are bound
as RiskArtifactHash. Header-only risk evidence retains `RiskModelVersion=null`;
the builder does not invent a value from absent rows.

Candidate and risk files are hashed again immediately before returning the
snapshot. Mutation during construction fails closed as `ARTIFACT_CHANGED`.

# 6. Portfolio State Validation

The first implementation accepts only explicit state supplied by its caller.
Required fields include Holdings, CashBalances, TotalPortfolioValue,
SourceStatus, ReconciliationStatus, and ValuationConventionVersion.

Safety controls include:

- exact decimal strings/integers only; binary floats are rejected;
- normalized unique Ticker and currency identifiers;
- non-negative finite quantities, prices, cash, and total value;
- valuation dates no later than PortfolioAsOfDate;
- PortfolioAsOfDate no later than candidate AsOfDate;
- first-contract cash restricted to BaseCurrency because no governed FX
  conversion exists;
- `SourceStatus=VERIFIED` and `ReconciliationStatus=PASS`; and
- exact reconciliation of holdings value plus cash to TotalPortfolioValue.

Empty holdings are permitted only when the caller explicitly supplies an empty
array as authoritative state. Missing holdings or cash are not converted to
zero.

# 7. Immutability and Collision Handling

`publish_snapshot()` serializes canonical UTF-8 JSON into a temporary sibling
file, flushes it, and uses an atomic same-filesystem hard-link operation to
create the target without overwrite.

If the target exists, publication raises
`PortfolioSnapshotCollisionError`. Identical content is not an exception to
the no-overwrite rule. Temporary files are removed after success or failure.

# 8. Fail-Closed Behavior

The module exposes `PortfolioSnapshotValidationError` with stable reason codes,
including:

- `ARTIFACT_UNREADABLE`;
- `ARTIFACT_SCHEMA_INVALID`;
- `ARTIFACT_CHANGED`;
- `SNAPSHOT_METADATA_MISSING`;
- `SNAPSHOT_METADATA_MIXED`;
- `SNAPSHOT_DATE_INVALID`;
- `RUN_ID_MISMATCH`;
- `AS_OF_DATE_MISMATCH`;
- `FUTURE_PORTFOLIO_STATE`;
- `INVALID_PORTFOLIO_VALUE`;
- `DUPLICATE_HOLDING`;
- `PORTFOLIO_RECONCILIATION_FAILED`;
- `CANDIDATE_ARTIFACT_INVALID`;
- `RISK_SNAPSHOT_MISMATCH`; and
- `REPOSITORY_PROVENANCE_UNAVAILABLE`.

Validation failure returns no snapshot and has no portfolio side effect.

# 10. Architecture and Safety Boundary

This implementation does not modify or connect:

- `score.py` or `trade_signal.py`;
- `production_candidate_builder.py` or `portfolio_candidate_adapter.py`;
- `portfolio_risk.py` or the point-in-time risk calculator;
- `position_sizing.py`;
- `order_draft.py` or `order_review.py`; or
- `daily_decision_report.py`.

Every snapshot contains:

```text
ValidationStatus = PASS
PermittedAction = NO_ACTION
```

`PASS` means provenance validation only. It does not mean candidate eligible,
risk READY, portfolio approved, or order authorized.
