# AI_investing V3.8.1 Phase 6B-8A Historical Shadow Archive Design

Design date: 2026-08-12

Status: design only. The archive is for research and validation. It does not
authorize trading or modify production behavior.

# 1. Purpose

Phase 6B-8A defines an immutable historical shadow archive for evidence needed
by future portfolio cutover-readiness reviews. The archive records what the
production-candidate and point-in-time risk path actually produced at a
decision date, including no-action, pending, and failed states.

The Phase 6B-7 audit found only one current zero-eligible snapshot. No real
one-eligible, multiple-eligible, READY/PASS, PENDING, or BLOCKED/FAILED
historical artifact set was available. Unit fixtures demonstrate implementation
mechanics but cannot establish production readiness. This archive closes the
evidence-preservation gap; it does not close migration blockers by itself.

Required eventual historical evidence includes:

- zero eligible candidates;
- one eligible candidate;
- multiple eligible candidates;
- READY/PASS risk;
- PENDING risk; and
- BLOCKED/FAILED risk.

# 2. Non-Production Boundary

The archive is downstream of the candidate, adapter, risk, and shadow outputs:

```text
production candidate artifacts
  -> validated candidate artifact
  -> point-in-time risk artifact
  -> shadow validation
  -> immutable archive copy and validation report
```

It must not:

- replace or feed `portfolio_risk.py`;
- change portfolio construction or position sizing;
- change FinalScore, TradeSignal, thresholds, eligibility, or risk formulas;
- promote WATCH or IGNORE to eligible;
- generate a synthetic investment signal;
- create a holding, TargetShares, OrderAction, or brokerage instruction;
- fill missing candidate, risk, or portfolio state; or
- treat archive completeness as approval to trade.

An archive decision such as READY means only “the captured shadow contract was
complete for validation.” It never means BUY, portfolio, sizing, order, or
execution approved.

# 3. Archive Principle

Historical records are append-only and content-addressed. Each canonical
record preserves:

- RunId;
- AsOfDate;
- ScoreModelVersion;
- RiskModelVersion;
- PortfolioSnapshotId;
- CandidateArtifactHash;
- RiskArtifactHash; and
- CreationTimestamp.

RunId and all model/snapshot identifiers describe decision provenance.
AsOfDate is the economic decision date. CreationTimestamp records when the
archive copy was created and must not affect decision logic, joining, or
identity.

No canonical historical record may be regenerated, refreshed, repaired, or
overwritten in place. If evidence later proves incorrect, retain the original,
mark it invalid through a separate append-only governance record, and create a
new review artifact outside the canonical date directory. Never silently
replace adverse or incomplete history.

# 4. Archive Structure

Required layout:

```text
archive/
└── shadow/
    └── YYYY-MM-DD/
        ├── candidates.csv
        ├── risk.csv
        ├── portfolio_snapshot.json
        ├── validation_report.md
        └── manifest.json
```

The directory name must equal AsOfDate in ISO `YYYY-MM-DD` format. V3.8.1
permits one canonical archive per decision date. Attempting to publish when
that directory already exists must fail closed, even when the new bytes appear
identical.

Failed capture attempts belong in an operational failure log outside
`archive/shadow/YYYY-MM-DD/`. Temporary files must not remain under the
canonical archive root.

## File responsibilities

| File | Responsibility |
|---|---|
| `candidates.csv` | Exact immutable production candidate rows for the decision date |
| `risk.csv` | Exact immutable point-in-time risk rows, including PENDING/BLOCKED/FAILED states |
| `portfolio_snapshot.json` | Pre-trade holdings/cash identity and AsOfDate provenance used by risk calculation |
| `validation_report.md` | Human-readable scenario, counts, contract results, failure reasons, and explicit no-action boundary |
| `manifest.json` | Machine-readable identity, hashes, schema versions, source references, and integrity result |

The archive directory is never a “latest” production source. Production code
must not discover or select archive records by filesystem modification time.

# 5. Immutable Publication Protocol

A future archive writer must follow this sequence:

1. Freeze already-generated source artifacts and the exact pre-trade portfolio
   snapshot; do not recompute candidate or risk values for archiving.
2. Validate AsOfDate and all provenance before allocating a target directory.
3. Reject an existing `archive/shadow/{AsOfDate}` target.
4. Create a temporary sibling directory.
5. Copy candidate and risk bytes without modifying values or row order.
6. Serialize the portfolio snapshot under a canonical JSON convention.
7. Validate contracts and generate the report and manifest.
8. Calculate SHA-256 hashes after every file is final.
9. Re-read every file and verify recorded hashes.
10. Atomically rename the complete temporary directory to `{AsOfDate}`.
11. Mark files read-only when supported and record archive verification status.

Any error before atomic publication produces no canonical record. An error
after publication cannot be repaired in place.

# 6. Manifest Contract

`manifest.json` must use UTF-8, sorted keys, deterministic separators, and
canonical date/timestamp representations.

## Required identity fields

| Field | Rule |
|---|---|
| `ArchiveContractVersion` | Deterministic archive schema identifier |
| `RunId` | Exact deterministic candidate RunId |
| `AsOfDate` | Exact decision date and directory name |
| `ScoreModelVersion` | Exact candidate score model version |
| `RiskModelVersion` | Exact approved risk model version, including zero-risk-row snapshots |
| `PortfolioSnapshotId` | Exact immutable pre-trade snapshot identity |
| `CandidateArtifactHash` | SHA-256 of canonical `candidates.csv` bytes |
| `RiskArtifactHash` | SHA-256 of canonical `risk.csv` bytes |
| `PortfolioSnapshotHash` | SHA-256 of canonical `portfolio_snapshot.json` bytes |
| `ValidationReportHash` | SHA-256 of final `validation_report.md` bytes |
| `CreationTimestamp` | UTC ISO-8601 informational timestamp |

## Required supporting fields

- repository commit and PROJECT_VERSION;
- candidate and risk schema versions;
- source artifact paths/names for lineage only;
- row counts and normalized ticker counts;
- eligible-candidate count;
- READY, PENDING, BLOCKED, FAILED, PASS, and validation-failure counts;
- captured scenario labels;
- observation and portfolio-state date checks;
- validation status and explicit reasons; and
- a controlled evidence action restricted to `NO_ACTION`.

CreationTimestamp, filesystem mtime, and host path are excluded from RunId and
artifact identity. Hashes must be verified whenever a record is read.

## Zero-row rule

RiskModelVersion and PortfolioSnapshotId remain mandatory when `risk.csv` has
only its header because zero candidates are eligible. They must come from the
approved run configuration and an explicit pre-trade snapshot, not from a
missing row and not from a guessed default.

# 7. Candidate Archive Contract

`candidates.csv` requires these fields:

| Field | Contract |
|---|---|
| `Ticker` | Normalized, non-empty, unique |
| `FinalScore` | Exact finite source value |
| `TradeSignal` | Exact controlled production value |
| `CandidateRank` | Exact deterministic production rank |
| `Eligibility` | Exact upstream ELIGIBLE/INELIGIBLE state |
| `RunId` | Exact deterministic run identity |
| `AsOfDate` | Exact decision date |
| `ScoreModelVersion` | Exact score lineage |

Additional existing candidate provenance fields may be retained, but required
fields cannot be dropped or renamed.

Rules:

1. Archive capture performs no score, rank, signal, or eligibility
   recalculation.
2. WATCH and IGNORE are never promoted.
3. CandidateRank is validated against the captured artifact contract but is
   not rewritten.
4. Duplicate normalized Ticker, mixed RunId/date/version, missing identity, or
   non-finite required values invalidate the archive attempt.
5. Manual CSV modification invalidates the hash and the record.
6. Zero candidates and zero eligible candidates retain a stable header.

If PortfolioEligible and adapter validation fields are archived as additional
columns, they remain exact upstream values. Archive validation cannot change
them.

# 8. Risk Archive Contract

`risk.csv` requires these fields:

| Field | Contract |
|---|---|
| `Ticker` | Normalized candidate identity |
| `RiskStatus` | Controlled archived risk state |
| `RiskModelVersion` | Exact deterministic risk lineage |
| `RiskAsOfDate` | Exact risk decision cutoff; must equal candidate AsOfDate |
| `PortfolioSnapshotId` | Exact pre-trade portfolio snapshot identity |

The archive should also preserve the existing source fields RunId,
ScoreModelVersion, RiskValidationStatus, RiskValidationReason,
ObservationEndDate, PortfolioAsOfDate, and all approved risk inputs. The
archive may map source AsOfDate to the explicit alias RiskAsOfDate only by an
auditable lossless copy; it must retain the original field or record the schema
mapping in the manifest. No fuzzy date conversion is allowed.

Allowed archived RiskStatus values:

- `READY`;
- `PENDING`;
- `BLOCKED`; and
- `FAILED`.

Compatibility with the current two-field source contract:

| Source condition | Archived interpretation |
|---|---|
| RiskStatus=READY and RiskValidationStatus=PASS | READY/PASS |
| RiskStatus=PENDING | PENDING; no action regardless of validation text |
| RiskStatus=BLOCKED | BLOCKED |
| Calculation/contract failure represented as a row | FAILED |
| RiskValidationStatus=FAILED with any inconsistent or unknown state | BLOCKED or FAILED, never READY |

READY is valid only with PASS validation, exact metadata, finite required risk
inputs, ObservationEndDate <= RiskAsOfDate, and PortfolioAsOfDate <=
RiskAsOfDate. Missing risk remains missing; it must not be converted into a
zero-risk row.

Forbidden fields and sources include legacy BacktestScore, trade SharpeRatio,
completed-trade MaxDrawdown, forward returns, and fabricated RiskLevel.

# 9. Portfolio Snapshot Contract

`portfolio_snapshot.json` must identify the state before any hypothetical
trade. Required content includes:

- PortfolioSnapshotId;
- PortfolioAsOfDate;
- candidate RunId and AsOfDate linkage;
- cash/account identity under an approved non-secret identifier;
- normalized holdings and weights used by risk calculation;
- deterministic holdings hash;
- source system/version; and
- CreationTimestamp as informational metadata.

PortfolioAsOfDate must be no later than AsOfDate. An empty portfolio is
represented by an explicit empty holdings collection and a valid snapshot
hash. Missing portfolio data is not equivalent to an empty portfolio and must
produce PENDING/BLOCKED evidence.

The JSON must not contain credentials, account numbers, personal identifiers,
or broker secrets.

# 10. Validation Report Contract

`validation_report.md` must be generated before publication and record:

- archive identity and all versions;
- candidate, eligible, and risk row counts;
- READY, PENDING, BLOCKED, FAILED, PASS, and validation-failure distributions;
- affected tickers and exact failure reasons;
- duplicate and metadata-integrity results;
- candidate/risk/portfolio date-boundary results;
- captured scenario and expected/observed result;
- deterministic ranking and ordering checks;
- archive hash-verification result;
- limitations and unavailable evidence; and
- `EvidenceAction: NO_ACTION`.

The report cannot state portfolio/order approval. For an invalid capture, no
canonical archive is published; a failure report may be written only to the
separate operational failure log.

# 11. Validation Scenarios

The validator must support the following real captured states. Contract unit
fixtures may test validator mechanics, but must be labeled synthetic and kept
outside the canonical historical archive. They cannot create synthetic
investment signals or satisfy historical readiness evidence.

## Scenario A — Zero eligible

Condition:

```text
eligible_candidates = 0
```

Expected:

- stable candidate and header-only risk contracts are allowed;
- zero READY and zero portfolio/action rows;
- validation result `NO_ACTION_REQUIRED`; and
- EvidenceAction remains `NO_ACTION`.

Zero denominators are reported as N/A, never 100%.

## Scenario B — Single eligible

Condition:

```text
eligible_candidates = 1
```

Verify exact candidate Ticker, rank, RunId, AsOfDate, ScoreModelVersion, risk
join, RiskModelVersion, PortfolioSnapshotId, and point-in-time dates.

Expected shadow evidence is either:

- `READY` only when the risk row is READY/PASS and all provenance validates;
  or
- `PENDING` with an explicit reason and no action.

Neither outcome authorizes a trade.

## Scenario C — Multiple eligible

Condition:

```text
eligible_candidates > 1
```

Verify:

- deterministic CandidateRank and ordering;
- duplicate rejection;
- one-to-one candidate/risk identity;
- stable results for identical captured inputs; and
- portfolio ranking and sizing prerequisites.

Sizing validation is read-only and isolated: it verifies that all required
inputs and approved caps could be supplied to a future controlled migration
without changing production sizing. It may validate deterministic hypothetical
weights in a non-ordering test harness only after a separate sizing contract is
approved. Until then, the report must state `SIZING_NOT_EVALUATED`; it must not
invent weights, shares, or orders.

## Scenario D — Risk failure

Examples:

- eligible candidate has no risk row;
- candidate/risk RunId, AsOfDate, ScoreModelVersion, RiskModelVersion, or
  PortfolioSnapshotId mismatch;
- stale risk or portfolio snapshot;
- RiskValidationStatus=FAILED;
- invalid/unknown risk state;
- future ObservationEndDate/PortfolioAsOfDate; or
- non-finite required risk input.

Expected:

- affected candidates are `BLOCKED` or `FAILED`;
- failure reasons remain distinct and auditable;
- zero production-ready/actionable rows; and
- EvidenceAction `NO_ACTION`.

# 12. Point-in-Time and Reproducibility Requirements

For decision date D:

- every market observation and indicator used must have Date <= D;
- RiskAsOfDate equals D;
- ObservationEndDate and PortfolioAsOfDate are <= D;
- the portfolio snapshot is pre-trade;
- no later universe, holding, filing, future return, or completed trade outcome
  is allowed; and
- no latest-row, nearest-date, forward-fill, backward-fill, or prior-snapshot
  repair is permitted.

Publication-date provenance is required for any future filing/fundamental
input. Reporting-period end alone does not prove availability at D.

Identical frozen source artifacts must reproduce the same candidate identity,
rank, risk classification, validation status, report metrics, and canonical
artifact hashes. CreationTimestamp may differ only in a separately executed
pre-publication replay; the first canonical publication remains immutable.
Any unexplained difference is `REPRODUCIBILITY_FAILED`.

# 13. Archive Validator Fail-Closed Rules

The validator must reject canonical publication for:

- an existing AsOfDate directory;
- missing or unexpected required files;
- missing manifest identity or hashes;
- hash mismatch or manual modification;
- mixed/missing RunId, AsOfDate, ScoreModelVersion, or RiskModelVersion;
- duplicate normalized candidate/risk key;
- CandidateArtifactHash or RiskArtifactHash mismatch;
- conflicting/missing PortfolioSnapshotId;
- stale/future candidate, risk, or portfolio dates;
- READY without PASS or without finite required risk inputs;
- missing risk for an eligible candidate unless captured explicitly as a
  BLOCKED failure scenario;
- unknown/inconsistent risk states;
- missing failure reason for PENDING/BLOCKED/FAILED;
- any future-data or fallback-repair evidence; or
- any position, share, order, or production-approval output.

Failure to archive a date is itself evidence and must appear in a separate
append-only capture-failure ledger. An adverse date must not disappear from the
observation calendar.

# 14. Acceptance Criteria

Phase 6B-8A design is complete when:

1. the exact archive directory and five-file contract are documented;
2. required manifest identities and hashes are defined;
3. candidate and risk schemas and no-recalculation rules are explicit;
4. zero, single, multiple, and risk-failure scenarios have deterministic
   expected outcomes;
5. point-in-time, immutability, reproducibility, and overwrite-rejection rules
   are defined;
6. the archive remains research-only and cannot authorize a portfolio or
   order;
7. no production behavior or Python module is changed; and
8. the existing test suite remains passing.

This design does not claim that historical evidence already exists. Archive
implementation and unbiased multi-date collection require separate approval.

# 15. Non-Goals and Next Boundary

Phase 6B-8A does not:

- replace `portfolio_risk.py`;
- migrate any portfolio consumer;
- change sizing, trading, scoring, eligibility, or risk rules;
- generate historical candidates retrospectively and label them observed;
- create synthetic investment signals;
- approve a controlled migration; or
- remove legacy research artifacts.

The next permissible phase is a standalone archive writer/validator with
overwrite, hash, point-in-time, scenario, and architecture-boundary tests. It
must remain disconnected from production consumers. Only later observed
multi-date evidence may be used by a new cutover-readiness audit.

Design conclusion: the archive exists to preserve uncomfortable evidence as
faithfully as favorable evidence. Missing risk, failed validation, and no-action
dates must be easier to discover than to erase. Until that record exists across
real decision dates, production readiness remains unproven.
