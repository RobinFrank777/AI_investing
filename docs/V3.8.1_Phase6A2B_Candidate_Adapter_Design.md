# AI_investing V3.8.1 Phase 6A-2B Candidate Adapter Design

Design date: 2026-08-12

Status: design only. No production code, score, threshold, signal, portfolio,
order, or backtest behavior is changed by this document.

## 1. Current Architecture

Two disconnected paths currently use the word “candidate.”

```text
Current production scoring

canonical OHLCV
  -> indicators
  -> score.py
  -> rank_stocks_v2.py
  -> trade_signal.generate_signals()
  -> results/stock_rank.csv
     [FinalScore, TradeSignal, Confidence, score components]
  -> technical report / top opportunities

Current portfolio candidate path

canonical OHLCV
  -> backtest_engine.py legacy technical filters
  -> fixed-holding historical performance
  -> IsQualified + BacktestScore
  -> results/backtest_qualified_20d.csv
  -> portfolio_risk.py
  -> model_portfolio.csv
  -> combined_scoring.py
  -> position_sizing.py
  -> order_draft.py
  -> order_review.py
  -> portfolio_action_report.py
  -> daily_decision_report.py
```

`portfolio_risk.load_qualified_candidates()` reads only the legacy qualified
backtest file and sorts it by `BacktestScore`. It never reads current
`FinalScore` or `TradeSignal`.

### Existing consumer requirements

| Consumer | Fields it currently assumes |
|---|---|
| `portfolio_risk.py` | Ticker, BacktestScore, MaxDrawdown, SharpeRatio; it adds RiskLevel, RiskWeightMultiplier, TargetWeight, TargetWeightPercent, PortfolioRole |
| `validate_portfolio_outputs.py` | Ticker, BacktestScore, AverageReturn, WinRate, MaxDrawdown, SharpeRatio plus portfolio-created fields |
| `combined_scoring.py` | Ticker, BacktestScore; combines it 70/30 with FundamentalScore |
| `position_sizing.py` | BacktestScore, TargetWeight, Ticker and merged fundamental fields; obtains LatestClose separately |
| `order_draft.py` | BacktestScore, fundamental/combined fields, risk/allocation fields, LatestClose and share calculations |
| `order_review.py` | Same draft contract plus action/status/value fields |
| `daily_decision_report.py` | Text outputs from technical report and portfolio action report; no structured provenance contract |

The candidate adapter can establish a correct source contract, but it cannot
alone make these legacy-named consumer contracts truthful. Consumer migration
must be explicit.

## 2. Target Architecture

```text
canonical OHLCV
  -> indicators
  -> score.py [ScoreModelVersion]
  -> rank_stocks_v2.py
  -> trade_signal.generate_signals()
  -> results/stock_rank.csv
  -> Candidate Adapter
       - validates source schema and finite values
       - enforces one AsOfDate and one ScoreModelVersion
       - rejects duplicate tickers
       - assigns deterministic rank
       - records signal state without recalculating it
       - applies an explicitly approved eligibility policy
       - emits stable empty output when no symbol is eligible
  -> results/production_candidates.csv
  -> Candidate Contract Validator
  -> portfolio construction adapter boundary
  -> portfolio construction
  -> position sizing
  -> order draft / review
  -> action and daily decision reports
```

The Candidate Adapter is a translation and validation boundary. It must not:

- calculate technical indicators or scores;
- call historical forward returns;
- reproduce BUY/WATCH conditions;
- change thresholds;
- fabricate legacy BacktestScore, MaxDrawdown, or SharpeRatio;
- calculate portfolio weights, shares, or order status; or
- use Investment Profile data.

### Proposed responsibilities

1. Read the current `stock_rank.csv` artifact produced by the ranking run.
2. Validate required columns, ticker uniqueness, one date, one score-model
   version, allowed signal values, and finite numeric fields.
3. Preserve `TradeSignal` exactly as emitted by production scoring.
4. Assign deterministic rank from descending FinalScore with ascending Ticker
   as the tie-breaker. The adapter must verify that this order is consistent
   with the source rather than changing score values.
5. Apply a separately approved eligibility policy and record its identifier.
6. Emit one row per input ticker, including ineligible rows and explicit
   reasons, or emit a header-only stable schema for an empty source. Portfolio
   construction should consume only rows with `EligibilityStatus=ELIGIBLE`.
7. Carry provenance fields into downstream artifacts.

Keeping ineligible rows in the adapter artifact makes zero-candidate outcomes
auditable; silently dropping them would obscure whether the source was empty,
stale, invalid, or simply contained no eligible signal.

## 3. Candidate Contract Definition

Proposed artifact: `results/production_candidates.csv`

Row grain: exactly one current production-scoring observation per ticker for a
single AsOfDate and RunId.

### Required fields

| Field | Type / constraints | Source | Purpose |
|---|---|---|---|
| `Ticker` | Non-empty normalized string; unique | `stock_rank.Ticker` | Security key |
| `AsOfDate` | ISO date; identical across rows | `MarketDataDate` | Market-data freshness boundary |
| `RunId` | Non-empty deterministic run identifier | New run metadata | Prevent cross-run artifact mixing |
| `ProjectVersion` | Non-empty version string | Runtime config | Release provenance |
| `ScoreModelVersion` | Exact non-empty identifier | `stock_rank.ScoreModelVersion` | Score contract provenance |
| `SignalPolicyVersion` | Deterministic identifier | New metadata, not new logic | Identifies unchanged BUY/WATCH policy |
| `EligibilityPolicyVersion` | Deterministic identifier | Adapter configuration/constant | Identifies approved candidate rule |
| `TradeSignal` | BUY, WATCH, or IGNORE | `stock_rank.TradeSignal` | Unmodified production state |
| `FinalScore` | Finite numeric | `stock_rank.FinalScore` | Production ranking score |
| `Rank` | Positive unique integer | Adapter-derived | Deterministic portfolio priority |
| `Confidence` | Finite numeric in existing scale | `stock_rank.Confidence` | Existing diagnostic context |
| `LatestClose` | Finite and > 0 | `stock_rank.Close` | Same-snapshot sizing price input |
| `EligibilityStatus` | ELIGIBLE or INELIGIBLE | Adapter-derived from approved policy | Explicit portfolio-admission result |
| `EligibilityReason` | Non-empty controlled text/code | Adapter-derived | Auditable admission decision |
| `CandidateStatus` | VALID or INVALID | Adapter validation | Separates data validity from eligibility |
| `CandidateMessage` | Empty or diagnostic text | Adapter validation | Invalid/degraded explanation |

### Optional diagnostic pass-through fields

`TrendScore`, `MomentumScore`, `VolumeScore`, `RS_Score`, `NearHighScore`,
`RawScore`, `20Day_Return`, `60Day_Return`, `Volume_Ratio`,
`DistanceToHigh`, `MA20`, and `MA60` may be retained for explainability. They
must not become new eligibility or portfolio rules in this migration.

### RiskInputs boundary

`RiskInputs` should not be a single opaque serialized field. If a future
approved portfolio risk contract requires inputs, each must be a named,
versioned column with defined units and source. Phase 6A-2B does not approve a
replacement for legacy MaxDrawdown/Sharpe-based RiskLevel.

Until that decision is made, the adapter should expose:

- `RiskContractVersion = UNRESOLVED`; and
- no fabricated `RiskLevel` or multiplier.

Portfolio activation must remain blocked until a compatible RiskLevel/allocation
contract is approved. Reusing the technical model's zero-valued `RiskScore`
would be semantically invalid.

### Eligibility decision gate

The adapter design supports an explicit policy but does not select one here.
The implementation phase must obtain approval for exactly one rule, such as:

- BUY-only eligibility; or
- another pre-existing, explicitly documented production policy.

WATCH must not silently become an order candidate, and IGNORE must never be
converted to BUY. The selected rule must have a version identifier and direct
boundary tests. This is a required governance decision, not an adapter default.

### Contract invariants

- One RunId, AsOfDate, ProjectVersion, ScoreModelVersion, signal-policy version,
  and eligibility-policy version per artifact.
- Unique normalized Ticker values.
- No NaN or infinity in required numeric fields.
- FinalScore and TradeSignal are copied, never recalculated.
- Rank is deterministic; `(Rank, Ticker)` ordering is stable.
- Invalid rows cannot be ELIGIBLE.
- A stale or mixed artifact fails closed; it is not partially consumed.
- Zero eligible rows is a valid header-preserving output and means no portfolio
  orders, not pipeline success by assumption.
- Candidate validation status and portfolio eligibility are separate concepts.

## 4. Field Mapping

| Legacy field | New source / disposition |
|---|---|
| `Ticker` | Map directly from production `Ticker` |
| `TotalRows` | Deprecate from production candidate contract; research metadata only |
| `BuySignalDays` | Deprecate; historical research only |
| `EntrySignalCount` | Deprecate; trade-event research only |
| `CompletedTradeCount` | Deprecate; research performance only |
| `AverageReturn` | Deprecate from eligibility; optional separately labeled research evidence |
| `WinRate` | Deprecate from eligibility; optional separately labeled research evidence |
| `BestTrade` / `WorstTrade` | Deprecate; research evidence only |
| `TotalReturn` / `CAGR` | Deprecate; research evidence only |
| `MaxDrawdown` / `SharpeRatio` | Do not map; current RiskLevel contract requires a separate governance decision |
| `Error` | Replace with structured `CandidateStatus` and `CandidateMessage` |
| `IsQualified` | Replace with versioned `EligibilityStatus` and `EligibilityReason` |
| `AverageReturnScore` | Deprecate |
| `WinRateScore` | Deprecate |
| `TradeCountScore` | Deprecate |
| Legacy `RiskScore` | Deprecate; it is a worst-trade performance subscore, not production RiskScore |
| `DrawdownScore` | Deprecate |
| `BacktestScore` | Deprecate; do not alias FinalScore to this name |
| `FinalScore` | Direct from `stock_rank.FinalScore` |
| `TradeSignal` | Direct from `stock_rank.TradeSignal` |
| `AsOfDate` | Rename from `stock_rank.MarketDataDate` |
| `Rank` | Derive deterministically from FinalScore and Ticker |
| `Confidence` | Direct from `stock_rank.Confidence` |
| `ScoreModelVersion` | Direct from production scoring output |
| `LatestClose` | Direct from the same ranking row's `Close`; eliminates a later unsynchronized reread |
| `RiskInputs` | No mapping until a named risk contract is approved |

### Required downstream terminology migration

| Current consumer field | Target field / decision |
|---|---|
| `BacktestScore` | `FinalScore`; update code, validators, and labels rather than aliasing |
| `CombinedScore = 0.7 × BacktestScore + 0.3 × FundamentalScore` | Governance decision required: preserving coefficients with a different score changes semantics; adapter must not decide it |
| `RiskLevel` from MaxDrawdown/Sharpe | New risk contract required or portfolio activation remains blocked |
| `RiskWeightMultiplier` | Remains portfolio logic after RiskLevel contract is approved |
| `TargetWeight*` | Remains portfolio-construction output, never adapter output |
| `LatestClose` reread from ticker CSV | Prefer adapter-carried same-AsOfDate Close; sizing must validate provenance |
| `Action = BUY` default | Must be guarded by adapter eligibility and source TradeSignal; exact rule requires approval |

## 5. Migration Plan

### Phase 1 — Contract and policy approval

1. Approve the row grain, required fields, naming, allowed values, and stable
   empty schema.
2. Approve the eligibility rule and assign `EligibilityPolicyVersion`.
3. Approve the replacement portfolio RiskLevel contract.
4. Decide how, or whether, fundamentals combine with production FinalScore.
   This decision belongs to score/portfolio governance, not field translation.
5. Define RunId generation and AsOfDate freshness tolerance.

### Phase 2 — Isolated adapter implementation

1. Add an independent candidate-adapter module and validator.
2. Read only `stock_rank.csv`; copy production signals and scores unchanged.
3. Emit `production_candidates.csv` without changing `portfolio_risk.py`.
4. Add direct tests for normal, empty, no-eligible, duplicate, mixed-date,
   mixed-version, stale, invalid-signal, NaN/infinity, and deterministic-rank
   cases.
5. Compare adapter rows to ranking rows and prove score/signal identity.

### Phase 3 — Shadow-mode comparison

1. Run legacy and new candidate sources side by side.
2. Report candidate-set and rank differences without allowing the adapter to
   create orders.
3. Verify metadata propagation and stable zero-candidate behavior.
4. Obtain human approval of the behavioral delta.

### Phase 4 — Portfolio consumer migration

1. Change `portfolio_risk.py` to consume the validated adapter contract.
2. Remove legacy qualification fields from the production model-portfolio
   schema and validators.
3. Implement only the separately approved risk and allocation contract.
4. Correct empty/all-Unknown/zero-multiplier/cap boundary behavior as its own
   reviewed portfolio correctness change.
5. Keep the legacy backtest modules and outputs available as research-only.

### Phase 5 — Downstream schema migration

1. Replace BacktestScore terminology in combined scoring, position sizing,
   orders, validators, cards, terminal, and reports.
2. Propagate RunId, AsOfDate, ProjectVersion, ScoreModelVersion, and policy
   versions through every output.
3. Require same-run/same-date compatibility before sizing or reporting.
4. Ensure missing fundamentals cannot silently receive a clean BUY approval.

### Phase 6 — Cutover validation

1. Run full unit, contract, pipeline, and clean-artifact end-to-end tests.
2. Verify no production module reads `backtest_qualified_20d.csv`.
3. Verify legacy results are labeled research-only in documentation and UI.
4. Verify zero eligible candidates create no orders and an explicit truthful
   report state.
5. Preserve a reviewed rollback point, then remove the legacy production
   configuration reference only after acceptance.

## 6. Risks

| Risk | Consequence | Design mitigation |
|---|---|---|
| Eligibility policy is assumed during coding | WATCH/IGNORE could become order candidates | Require policy approval and version before activation |
| FinalScore is renamed BacktestScore | Semantically false reports and formulas | Use explicit FinalScore field throughout |
| Existing 70/30 combined formula is reused automatically | Unreviewed change in fundamental/technical meaning | Separate governance decision and comparison |
| RiskLevel inputs disappear | Allocation division-by-zero or all-Unknown behavior | Block activation until risk contract and boundary handling are approved |
| LatestClose is reread after ranking | Price/date mismatch during sizing | Carry and validate same-snapshot Close and AsOfDate |
| Stale `stock_rank.csv` is accepted | Orders based on old signals | RunId/AsOfDate/freshness fail-closed checks |
| Mixed score-model versions | Incomparable candidates | Single-version invariant |
| Duplicate or malformed tickers | Duplicate positions/orders | Normalize and reject duplicates |
| NaN/infinity sorts or passes rules | Invalid candidates reach allocation | Finite-value validation before eligibility |
| No eligible candidates | Empty-order crashes or false READY status | Stable schemas and explicit NO_ELIGIBLE_CANDIDATES state |
| Rank ties depend on input order | Non-reproducible selection at MAX_HOLDINGS | Ticker tie-breaker and direct tests |
| Adapter recalculates signal logic | Production/adapter drift | Copy and verify TradeSignal; never reproduce thresholds |
| Legacy metrics remain visible | Users may infer they validate production BUY | Remove from production schemas and label research-only |
| Fundamental data is missing | Missing data may be treated as approval | Fail closed or explicit review state under separate policy |
| Large candidate-set change at cutover | Unexpected portfolio/order delta | Shadow mode and human-reviewed comparison |
| Metadata fields stop before reports | Mixed artifacts remain possible | End-to-end required-field propagation and validators |

### Design conclusion

The Candidate Adapter is feasible as a narrow, testable boundary, but the full
production cutover is **not** a simple input-file substitution. Three decisions
must precede activation: candidate eligibility, portfolio RiskLevel/allocation
inputs, and the role of fundamentals relative to FinalScore. Keeping these
decisions outside the adapter prevents a data-contract migration from silently
becoming a strategy or portfolio-policy change.
