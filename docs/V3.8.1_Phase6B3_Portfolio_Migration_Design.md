# AI_investing V3.8.1 Phase 6B-3 Portfolio Migration Design

Design date: 2026-08-12

Status: design only. This document does not modify production code, portfolio
rules, score logic, thresholds, risk formulas, position sizing, or order logic.

# 1. Current Architecture

## Production candidate path

```text
results/stock_rank.csv
  -> production_candidate_builder.py
  -> results/production_candidates.csv
  -> portfolio_candidate_adapter.py
  -> results/validated_portfolio_candidates.csv
```

The validated contract carries Ticker, AsOfDate, RunId, ScoreModelVersion,
CandidateRank, FinalScore, TradeSignal, Eligibility, PortfolioEligible,
ValidationStatus, and ValidationReason. Only BUY plus ELIGIBLE can cross the
signal boundary. Accepted rows remain explicitly `RISK_INPUT_PENDING`.

## Active portfolio path

```text
results/backtest_qualified_20d.csv
  -> portfolio_risk.load_qualified_candidates()
  -> portfolio_risk.build_model_portfolio()
  -> results/model_portfolio.csv
  -> combined_scoring.py
  -> results/combined_score.csv
  -> position_sizing.py
  -> results/model_portfolio_sizing.csv
  -> order_draft.py
  -> results/order_draft.csv
  -> order_review.py
  -> results/order_review.csv
  -> portfolio_action_report.py
  -> daily_decision_report.py
```

The two paths are not connected. The active portfolio ranks legacy candidates
by BacktestScore, derives RiskLevel from MaxDrawdown and SharpeRatio, and
propagates legacy fields through sizing, orders, validators, and reports.

# 2. Target Architecture

```text
validated_portfolio_candidates.csv
  -> validated-candidate contract check
       identity, provenance, finite values, BUY lineage
  -> portfolio risk input join
       same Ticker + RunId + AsOfDate, approved risk contract only
  -> portfolio_risk.py
       eligible + risk-ready rows only
       CandidateRank priority
       existing approved allocation rules
       stable zero-row output
  -> model_portfolio.csv
       FinalScore terminology + provenance + weights
  -> optional fundamental decision boundary
       separately approved; no implicit legacy formula reuse
  -> position_sizing.py
       synchronized positive price + approved TargetWeight
  -> model_portfolio_sizing.csv
  -> order_draft.py
       eligible BUY lineage, positive whole shares, DRAFT_ONLY
  -> order_review.py
       fail-closed row and portfolio validation
  -> action report / daily decision report
       truthful no-action state + provenance compatibility
```

## Boundary responsibilities

| Boundary | Responsibility | Must not do |
|---|---|---|
| Production candidate builder | Reproduce current score/signal snapshot and deterministic rank | Portfolio allocation or risk assessment |
| Portfolio candidate adapter | Validate provenance and enforce BUY+ELIGIBLE signal boundary | Fabricate risk or performance fields |
| Risk input provider | Measure approved, point-in-time portfolio-risk inputs | Decide candidate eligibility or recalculate FinalScore |
| Risk join/validator | Require same identity/provenance; set risk readiness | Fill missing inputs silently |
| Portfolio construction | Apply MAX_HOLDINGS, exposure caps, and approved risk weighting | Use legacy backtest qualification |
| Position sizing | Convert approved weights and synchronized prices into whole shares | Admit candidates or change scores |
| Order draft | Translate valid positive positions into DRAFT_ONLY BUY rows | Approve execution |
| Order review | Enforce hard row/portfolio safety checks | Treat missing/non-finite data as PASS |
| Reports | Display decisions and provenance truthfully | Infer PASS from artifact presence or mtime |

Candidate eligibility and portfolio risk assessment remain separate:

- Eligibility answers: “Does the current production signal permit this symbol
  to reach the portfolio boundary?”
- Risk assessment answers: “Given an eligible symbol and current portfolio
  context, is sufficient risk information available, and what approved
  allocation treatment applies?”

A candidate can be signal-eligible while remaining ineligible for construction
because risk input is pending, invalid, or incompatible.

# 4. Risk Contract Design

## Proposed artifact boundary

Proposed artifact name: `results/portfolio_risk_inputs.csv`.

Row grain: one risk assessment per Ticker for the exact candidate RunId and
AsOfDate. The provider and formula are not selected in this design.

### Identity and governance fields

| Field | Requirement |
|---|---|
| `Ticker` | Normalized, non-empty, unique |
| `RunId` | Must exactly match candidate RunId |
| `AsOfDate` | Must exactly match candidate AsOfDate |
| `RiskModelVersion` | Required deterministic identifier |
| `RiskStatus` | `READY`, `PENDING`, or `INVALID` |
| `RiskReason` | Explicit reason, required unless READY |
| `ObservationEndDate` | Must not exceed AsOfDate |

### Possible quantitative inputs

These are contract categories for separate approval, not implemented formulas:

| Category | Candidate fields | Required definition before use |
|---|---|---|
| Volatility | `Volatility20D`, optionally longer horizon | Return convention, window, minimum observations, annualization |
| Drawdown | `TrailingDrawdown`, `MaximumDrawdownWindow` | Window, price/total-return basis, missing-data treatment |
| Liquidity | `AverageDollarVolume`, `VolumeCoverage` | Window, minimum threshold, split handling, currency |
| Concentration | `CurrentTickerWeight`, `SectorWeight`, `IssuerExposure` | Current holdings source, taxonomy, limits |
| Correlation | `PortfolioCorrelation`, `CorrelationCoverage` | Lookback, benchmark/portfolio series, minimum overlap |
| Fundamental risk | `FundamentalRiskStatus` or named inputs | Independent source, freshness, allowed missing states; never Investment Profile prose |

### Derived assessment fields

After formula approval, a risk evaluator may emit:

- `RiskLevel` using a controlled vocabulary;
- `RiskWeightMultiplier` under existing or separately approved limits; and
- `RiskAssessmentStatus` and `RiskAssessmentReason`.

No default value should exist for missing risk data. `PENDING` or `INVALID`
must make the row construction-ineligible. All-Unknown/zero-multiplier cases
must produce a stable zero-position result rather than division by zero.

### Required invariants

- Candidate and risk identity metadata match exactly.
- Risk observations use data available no later than AsOfDate.
- Required numerics are finite and have explicit units/ranges.
- Missing coverage is not zero-filled.
- Risk readiness cannot alter TradeSignal, Eligibility, FinalScore, or rank.
- Candidate eligibility cannot imply risk readiness.
- Investment Profile remains presentation-only unless a separately approved,
  structured fundamental-risk source is introduced.

# 5. Position Sizing Contract

## Target input fields

| Field | Classification | Source / treatment |
|---|---|---|
| `Ticker` | Already available | Validated candidate, propagated through portfolio |
| `RunId`, `AsOfDate`, `ScoreModelVersion` | Already available | Must propagate unchanged |
| `CandidateRank`, `FinalScore`, `TradeSignal` | Already available | Context/lineage; not recalculated |
| `PortfolioEligible` | Already available | Must be true before construction |
| `RiskModelVersion`, `RiskStatus` | Needs adapter/join | Approved risk contract |
| `RiskLevel`, `RiskWeightMultiplier` | Needs new calculation | Risk evaluator, not candidate adapter |
| `TargetWeight` | Needs portfolio calculation | Existing portfolio limits after risk readiness |
| `AccountValue` | Already configured | `config.ACCOUNT_VALUE`; validate finite and positive |
| `LatestClose` | Needs synchronized price adapter | Same AsOfDate market snapshot; finite and > 0 |
| `PriceAsOfDate` | Needs adapter | Must equal approved execution/sizing date contract |
| `TargetDollarAmount` | Existing calculation | TargetWeight × AccountValue |
| `TargetShares` | Existing calculation | Whole, non-negative; zero means no order |
| `EstimatedPositionValue` | Existing calculation | Shares × LatestClose |
| `PositionCashRemainder` | Existing calculation | Target amount minus estimated value |
| `BacktestScore` | Remove | Replaced by truthful FinalScore lineage |
| Legacy performance columns | Remove | Research-only |
| `FundamentalScore`, `CombinedScore`, rating | Separate decision | Do not reuse legacy 70/30 formula automatically |

## Sizing safety requirements

- Stable header-only output for zero positions.
- No NaN or infinity in price, weight, account, share, or value fields.
- `LatestClose > 0`; price source date and RunId compatibility are explicit.
- TargetWeight is finite, non-negative, individually capped, and total exposure
  does not exceed configured maximum.
- TargetShares is an exact non-negative integer.
- Zero shares are retained as a no-order reason or filtered into a separate
  auditable no-order result; they never enter an executable draft.
- Duplicate tickers are rejected before allocation.
- Unknown/pending risk rows cannot consume valid holding slots.
- Empty and all-pending cases produce cash-only/no-action output.

# 6. Order Workflow Contract

## Mandatory draft fields before an order exists

### Provenance

- `Ticker`, `RunId`, `AsOfDate`, `ScoreModelVersion`, `RiskModelVersion`;
- `CandidateRank`, `FinalScore`, `TradeSignal`, `PortfolioEligible`;
- `PriceAsOfDate` and source identifier.

### Approval lineage

- `TradeSignal == BUY`;
- source `Eligibility == ELIGIBLE`;
- `PortfolioEligible == True`;
- candidate adapter status demonstrates validated lineage;
- `RiskStatus == READY`; and
- no missing-fundamental state may silently become clean approval if
  fundamentals remain part of the approved policy.

### Position and value

- finite `TargetWeight`, `LatestClose`, `TargetDollarAmount`,
  `EstimatedOrderValue`, and remainder;
- `LatestClose > 0`;
- positive whole `TargetShares` for an actual draft;
- EstimatedOrderValue equals TargetShares × LatestClose;
- per-order, order-count, total-order-value, position, and total-exposure limits
  are satisfied or explicitly sent to REVIEW/BLOCKED under existing policy;
- `Action=BUY` and `OrderStatus=DRAFT_ONLY` remain explicit.

## Review outcomes

- Any missing, NaN, infinity, invalid price/share, broken provenance, mixed
  RunId/date/version, pending risk, or inconsistent formula must be BLOCKED.
- Existing high-risk or oversized cases remain REVIEW unless separately
  changed; this design does not alter their rules.
- Empty orders are a valid `NO_ORDERS` state with stable schemas, zero totals,
  and no row-zero indexing.
- An empty action report must say `NO ORDERS — NO ACTION`, never READY FOR
  MANUAL CONFIRMATION.
- Daily decision report must require compatible provenance between technical
  screening, portfolio action, and validation artifacts; filesystem mtime is
  not a sufficient join key.

## Output propagation

RunId, AsOfDate, score/risk model versions, and validation status must survive
order draft, order review, action report, and daily decision report. Reports
must distinguish:

- pipeline execution status;
- candidate eligibility;
- risk readiness;
- order review status; and
- no-action state.

# 7. Migration Plan

## Phase A — Adapter introduction

Status: candidate adapters exist; portfolio integration remains disabled.

1. Freeze and document current production and validated-candidate schemas.
2. Add explicit configured paths for both artifacts without changing the
   active portfolio source.
3. Define and approve risk-input, price snapshot, and fundamentals contracts.
4. Add standalone validators for candidate/risk identity compatibility.
5. Preserve stable zero-row artifacts and test the current zero-eligible case.

Exit criterion: adapters and risk/price contracts validate independently; no
production order path consumes them.

## Phase B — Dual validation

1. Generate legacy and production-candidate portfolio inputs side by side.
2. Build a shadow production portfolio that cannot create order files.
3. Compare candidate membership, ordering, risk readiness, weights, zero-row
   behavior, and rejection reasons.
4. Do not compare BacktestScore numerically to FinalScore as if equivalent.
5. Exercise missing, stale, duplicate, all-pending, non-finite, invalid-price,
   zero-share, and empty-order scenarios end to end.
6. Require human acceptance of all behavioral differences.

Exit criterion: shadow outputs are deterministic, bounded, provenance-complete,
and safe; legacy remains the active source.

## Phase C — Portfolio consumer switch

1. Change `portfolio_risk.py` input to the validated eligible+risk-ready
   contract and CandidateRank priority.
2. Update model-portfolio schema/validator to FinalScore terminology and
   provenance; remove legacy performance requirements.
3. Implement safe zero/all-pending/zero-multiplier and duplicate behavior while
   preserving approved portfolio limits.
4. Migrate position sizing to synchronized positive price input and stable
   empty outputs.
5. Migrate draft/review schemas and validators to fail-closed provenance and
   finite-value checks.
6. Update action/daily reports to truthful no-action and compatible-run states.
7. Run a clean current snapshot. With zero eligible candidates, expected output
   is cash-only/no orders—not a crash and not READY.

Exit criterion: no production portfolio/order consumer reads or requires
legacy candidate fields.

## Phase D — Legacy dependency removal

1. Remove `BACKTEST_QUALIFIED_20D_OUTPUT_PATH` from production portfolio
   configuration/imports.
2. Remove BacktestScore and legacy performance fields from production schemas,
   validators, displays, documentation, and tests.
3. Retain `backtest_engine.py`, its artifacts, and validation as explicitly
   research-only.
4. Search the full repository to prove no production consumer cites legacy
   qualification as production BUY validation.
5. Run full regression and clean end-to-end portfolio/report validation before
   release preparation.

Exit criterion: legacy backtest behavior remains available for research but has
no authority over production candidate, portfolio, order, or status decisions.

# 8. Release Blockers

| Blocker | Severity | Resolution phase |
|---|---|---|
| Active portfolio still reads legacy qualified backtest candidates | High | Phase C/D |
| Risk-input/RiskLevel contract is not approved | High | Phase A |
| Fundamentals-versus-FinalScore policy is unresolved | High if fundamentals remain in order chain | Phase A/B |
| Current zero-eligible snapshot is not safe through sizing/orders/reports | High | Phase B/C |
| NaN order values can currently receive PASS | Critical | Phase C |
| All-Unknown/zero multiplier produces NaN weights | High | Phase C |
| Missing score can receive allocation | High | Phase C |
| Infinite/non-positive price is not rejected | High | Phase B/C |
| Duplicate tickers can consume holding slots | High | Phase B/C |
| Missing fundamentals can silently flow toward BUY/PASS | High | Phase A/C |
| Empty orders can crash validation or imply READY | High | Phase C |
| RunId/AsOfDate/model versions are not propagated | High | Phase C |
| BacktestScore terminology remains in production outputs/reports | Medium | Phase C/D |

Design conclusion: the safe migration unit is the complete portfolio-to-report
contract, staged behind dual validation. Switching only the input filename or
aliasing FinalScore to BacktestScore would leave unresolved risk semantics,
unsafe empty/non-finite behavior, and misleading downstream outputs.
