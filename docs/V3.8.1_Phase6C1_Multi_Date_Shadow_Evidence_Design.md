# AI_investing V3.8.1 Phase 6C-1 Multi-Date Shadow Evidence Framework Design

Design date: 2026-08-12

Status: design only. No archive writer, production consumer, scoring rule,
trading rule, risk formula, portfolio rule, sizing rule, or order behavior is
implemented or changed by this document.

# 1. Purpose and Scope

Phase 6C-1 defines a reproducible historical evidence framework for observing
the production-candidate and point-in-time risk path across multiple decision
dates. Its purpose is to answer whether the new path behaves safely under
normal, empty, incomplete, invalid, and provenance-conflict conditions.

The audited evidence path is:

```text
results/stock_rank.csv
  -> production_candidate_builder.py
  -> results/production_candidates.csv
  -> portfolio_candidate_adapter.py
  -> results/validated_portfolio_candidates.csv
  -> portfolio_risk_calculator.py
  -> results/portfolio_risk_inputs.csv
  -> shadow_validation.py
  -> results/shadow_validation_report.csv
  -> immutable shadow archive
```

The framework is non-production. It creates evidence only and cannot:

- migrate or feed `portfolio_risk.py`;
- create portfolio holdings, weights, shares, or orders;
- change FinalScore, TradeSignal, BUY/WATCH thresholds, or eligibility;
- fabricate missing candidate, risk, universe, or portfolio data;
- create RiskLevel or a risk multiplier;
- use shadow results to authorize a production action; or
- select dates or rules because they produce favorable performance.

The framework observes decisions; it does not improve or approve them. When
evidence is absent or contradictory, the correct state is no action and an
explicit insufficient-evidence result.

# 2. Shadow Archive Contract

Archive root:

```text
shadow_archive/
  {AsOfDate}/
    metadata.json
    production_candidates.csv
    validated_portfolio_candidates.csv
    portfolio_risk_inputs.csv
    shadow_validation_report.csv
```

`{AsOfDate}` uses ISO `YYYY-MM-DD` and represents the decision date, not the
archive creation date. One governed canonical snapshot is permitted per
AsOfDate in V3.8.1. If a directory already exists, a second write must fail
closed. Correction or replay evidence must be stored outside the canonical
path under a separately approved quarantine/review process; it must never
replace the original silently.

## Required artifact roles

| File | Required content | Prohibited content/behavior |
|---|---|---|
| `metadata.json` | Snapshot identity, provenance, hashes, scenario labels, evidence metrics, validation result | Trading approval, guessed metadata, mutable “latest” pointer |
| `production_candidates.csv` | Exact output of the production candidate builder for the snapshot | Re-ranked or retrospectively filtered rows |
| `validated_portfolio_candidates.csv` | Exact candidate-adapter output | Promoted eligibility or fabricated risk fields |
| `portfolio_risk_inputs.csv` | Exact point-in-time risk-calculator output | Forward returns, legacy BacktestScore/Sharpe/MaxDrawdown, fabricated RiskLevel |
| `shadow_validation_report.csv` | Shadow-only classifications plus mandatory snapshot summary | Position sizing, holdings, order actions, production approval |

The archive intentionally begins at `production_candidates.csv`. The upstream
`stock_rank.csv`, point-in-time universe definition, portfolio snapshot, market
data manifest, source code revision, and configuration remain mandatory source
evidence and are referenced by immutable hashes in `metadata.json`. If any
referenced source cannot be preserved or resolved, the snapshot cannot qualify
as point-in-time evidence.

# 3. Immutability and Write Protocol

Historical evidence must be append-only.

Required write sequence:

1. Resolve and validate AsOfDate before creating an archive target.
2. Reject the run if `shadow_archive/{AsOfDate}` already exists.
3. Create a temporary sibling directory, never the canonical directory.
4. Generate all CSV artifacts from frozen input copies.
5. Validate schemas, exact provenance, point-in-time bounds, scenarios, and
   stable ordering.
6. Calculate SHA-256 for every archived CSV and every referenced source
   manifest.
7. Write canonical JSON metadata with sorted keys and the hashes.
8. Re-read every file and verify its recorded hash.
9. Atomically rename the completed temporary directory to `{AsOfDate}`.
10. Mark the snapshot read-only where the platform supports it and record the
    immutable repository revision.

Failure before the atomic rename leaves no canonical snapshot. Failure after
creation marks the snapshot invalid for review; it does not authorize an
in-place repair. Archive verification must detect missing files, extra
unexpected files, hash changes, mixed provenance, and directory/AsOfDate
disagreement.

The archive root is research evidence, not a production input directory. No
production consumer may resolve “latest” from it by filename or mtime.

# 4. Metadata Contract

Each `metadata.json` must contain at minimum:

| Field | Type / rule | Meaning |
|---|---|---|
| `RunId` | Required deterministic string | Exact candidate run identity |
| `AsOfDate` | Required ISO date | Decision date and archive directory name |
| `ScoreModelVersion` | Required deterministic string | Score lineage shared by candidate/risk rows |
| `RiskModelVersion` | Required deterministic string | Risk-calculator lineage; explicit even for zero risk rows |
| `UniverseVersion` | Required deterministic string | Point-in-time universe identity/version or content hash |
| `PortfolioSnapshotId` | Required deterministic string | Immutable pre-trade portfolio state; explicit no-holdings snapshot is valid, missing is not |
| `GeneratedTimestamp` | Required UTC ISO-8601 timestamp | Informational archive creation time only |

## Required supporting metadata

To make the minimum fields auditable, the JSON must also record:

- `ArchiveContractVersion`;
- `RepositoryCommit` and `ProjectVersion`;
- `ScenarioLabels` and whether each is observed, controlled synthetic, or
  deliberately invalid;
- `SourceHashes`, including stock-rank input, universe manifest, point-in-time
  market-data manifest, portfolio snapshot, relevant configuration, and code;
- `ArtifactHashes` for all four archived CSV files;
- `RowCounts` for every artifact;
- `EvidenceMetrics` under the contract in section 9;
- `PointInTimeValidation` results;
- `ReproducibilityValidation` results;
- `SnapshotValidationStatus` and explicit `SnapshotValidationReasons`; and
- `FrameworkResult` under section 10.

## Deterministic identity rules

RunId must be derived from canonical decision inputs, not GeneratedTimestamp,
filesystem mtime, row input order, or random state. The existing production
candidate RunId remains authoritative and must match every candidate/risk
reference. A recommended verification formula is:

```text
candidate-{YYYYMMDD}-{first_12_hex_of_SHA256(canonical_candidate_input)}
```

The framework verifies this identity; it does not replace it with a shadow
RunId. If independently needed, `SnapshotId` may be derived from AsOfDate,
RunId, ScoreModelVersion, RiskModelVersion, UniverseVersion,
PortfolioSnapshotId, source hashes, and artifact hashes. GeneratedTimestamp
must be excluded.

AsOfDate is the economic decision cutoff. GeneratedTimestamp is informational
only: it cannot determine market cutoff, universe membership, portfolio state,
join selection, ordering, or readiness.

## Zero-row metadata

RiskModelVersion and PortfolioSnapshotId remain mandatory when zero candidates
are eligible. They identify the approved calculator and the pre-trade state
against which the no-action decision was made. They must come from the run
configuration and immutable snapshot—not be inferred from absent CSV rows.

# 5. Candidate, Risk, and Join Contracts

## Candidate contract

The archive validator must confirm:

- normalized unique Ticker;
- one RunId, AsOfDate, and ScoreModelVersion per snapshot;
- finite FinalScore and CandidateRank;
- CandidateRank is exactly deterministic under FinalScore descending then
  Ticker ascending;
- identical source values for FinalScore and TradeSignal across the builder and
  adapter boundary;
- only BUY + ELIGIBLE can set PortfolioEligible=True; and
- zero rows and zero eligible rows retain stable schemas.

## Risk contract

The archive validator must confirm:

- one row at most per Ticker + RunId + AsOfDate;
- exact candidate RunId/AsOfDate/ScoreModelVersion compatibility;
- deterministic RiskModelVersion;
- PortfolioSnapshotId and PortfolioAsOfDate provenance;
- ObservationEndDate no later than AsOfDate;
- finite required approved risk inputs for READY/PASS;
- explicit reasons for PENDING/FAILED and BLOCKED/FAILED; and
- absence of BacktestScore, forward returns, completed-trade MaxDrawdown,
  legacy SharpeRatio, and fabricated RiskLevel.

## Shadow join contract

The join key is exactly:

```text
Ticker + RunId + AsOfDate
```

Ticker-only, fuzzy-date, nearest-date, latest-row, forward-fill, backward-fill,
and prior-snapshot fallback are forbidden. ScoreModelVersion compatibility is
validated after the exact join. Missing risk and metadata mismatch remain
distinct failures.

# 6. Required Shadow Scenarios

The framework must support and archive the following cases. A scenario may be
an observed historical snapshot or a controlled synthetic fixture; metadata
must label which. Synthetic evidence verifies mechanics but cannot substitute
for an operational observation window.

## Scenario A — Zero eligible candidates

Input condition:

- zero PortfolioEligible rows.

Expected evidence:

- stable candidate, risk, and shadow schemas;
- zero SHADOW_READY rows;
- `NO_PORTFOLIO_ELIGIBLE_CANDIDATE`; and
- framework decision `NO_ACTION`.

Coverage percentages whose denominator is zero are `null`/N/A, not 100%.

## Scenario B — Single eligible candidate

Verify:

- exact Ticker, RunId, AsOfDate, and ScoreModelVersion identity;
- CandidateRank and source FinalScore/TradeSignal preservation;
- exact risk join and RiskModelVersion;
- portfolio and market provenance; and
- deterministic shadow classification.

SHADOW_READY is permitted only for exact metadata plus READY/PASS and valid
point-in-time dates. It remains shadow evidence, not production approval.

## Scenario C — Multiple eligible candidates

Verify:

- deterministic ranking by FinalScore descending then Ticker ascending;
- duplicate normalized Ticker/composite-key rejection;
- stable output ordering independent of input row order;
- one-to-one risk joins; and
- deterministic counts and classifications.

## Scenario D — Risk pending

Example input: `RiskStatus=PENDING` and `RiskValidationStatus=FAILED` with an
explicit reason.

Expected evidence:

- shadow result remains blocked from action (`SHADOW_PENDING` is acceptable as
  the diagnostic class);
- framework action is `NO_ACTION`; and
- no portfolio-ready, position, or order field is created.

## Scenario E — Risk failed

Example input: `RiskValidationStatus=FAILED`, including BLOCKED/FAILED or an
invalid status combination.

Expected evidence:

- `SHADOW_BLOCKED` or stricter snapshot invalidation;
- original and standardized failure reason retained;
- framework action `NO_ACTION`; and
- no replacement value or promotion.

## Scenario F — Metadata mismatch

Example: candidate RunId=A and risk RunId=B for the same ticker/date.

Expected evidence:

- no exact join;
- `SHADOW_METADATA_MISMATCH` with `RUN_ID_MISMATCH`;
- zero SHADOW_READY for the affected candidate; and
- framework action `NO_ACTION`.

Equivalent AsOfDate and ScoreModelVersion mismatch fixtures are required.

# 7. Point-in-Time Evidence Contract

For a snapshot with AsOfDate D, every source must prove its availability at D.

## Market boundary

- Every OHLCV observation used has `Date <= D`.
- ObservationEndDate is recorded per READY/PASS risk row and is <= D.
- The market-data manifest records per-ticker source path/hash, earliest date,
  latest available date, observation count, and exact rows/window hash used.
- Indicators and risk inputs are derived only from the truncated history.

Forbidden:

- future OHLCV or indicators;
- future universe membership;
- later portfolio holdings or post-trade weights;
- forward returns and completed future trade outcomes;
- future fundamentals based only on a reporting-period date;
- filling missing history from a later snapshot; and
- latest/nearest artifact substitution.

## Portfolio boundary

- PortfolioSnapshotId resolves to an immutable pre-trade holdings/cash state.
- PortfolioAsOfDate is <= D.
- A zero-holdings snapshot is explicit and hashed; absence is not treated as
  zero holdings.
- Later holdings cannot be substituted for an earlier decision.

## Leakage challenge evidence

Each code/model version must retain tests proving:

1. dramatic mutation of all OHLCV rows after D cannot change D results;
2. future-row append cannot change D results;
3. future portfolio state is rejected;
4. different AsOfDate/RunId cannot join; and
5. any ObservationEndDate after D is blocked.

Each archived snapshot additionally records the applicable test-suite revision
and result. A generic passing test suite cannot repair incomplete snapshot
provenance.

# 8. Reproducibility Contract

Identical frozen inputs must be run twice in isolated temporary output
directories before the canonical archive is published.

The following must be identical:

- RunId and AsOfDate;
- candidate row set, values, ranking, and ordering;
- validated candidate values and PortfolioEligible classification;
- risk row set, deterministic risk fields, RiskStatus,
  RiskValidationStatus, and reasons;
- shadow row set, ordering, ShadowStatus, and ShadowReason;
- evidence metrics and framework result; and
- canonical CSV hashes after excluding explicitly informational fields.

Permitted difference:

- `GeneratedTimestamp` in metadata.

The existing risk `CalculationTimestamp` is operational audit metadata rather
than a classification input. Until its deterministic comparison convention is
explicitly approved, canonical replay comparison must normalize it to the
original frozen run value or report it as an additional informational
difference. It must never be silently ignored while claiming byte-identical
artifacts.

CSV canonicalization must define UTF-8 encoding, line ending, exact column
order, stable row order, null representation, date representation, float
serialization, and terminal newline. JSON canonicalization must use UTF-8,
sorted keys, deterministic separators, and no GeneratedTimestamp in identity
hashes.

Any unexplained difference is `REPRODUCIBILITY_FAILED` and invalidates that
snapshot for readiness evidence.

# 9. Evidence Metrics Contract

Every archived `shadow_validation_report.csv` must contain exactly one
snapshot summary record even when there are zero eligible candidates. Detail
records may follow. A required `RecordType` field distinguishes `SUMMARY` from
`DETAIL`, preventing a fabricated ticker row from representing an empty state.

The SUMMARY record contains at minimum:

## Candidate metrics

- `total_candidates`;
- `eligible_candidates` (source Eligibility=ELIGIBLE);
- `portfolio_eligible` (PortfolioEligible=True).

## Risk metrics

- `risk_rows`;
- `READY`;
- `PENDING`;
- `BLOCKED`.

## Validation metrics

- `PASS`;
- `FAILED`;
- `metadata_mismatch`;
- `missing_risk`.

Also required for interpretability:

- exact matched eligible count;
- orphan risk count;
- SHADOW_READY, SHADOW_PENDING, SHADOW_BLOCKED,
  SHADOW_MISSING_RISK, and SHADOW_METADATA_MISMATCH counts;
- exact-match and shadow-ready denominators and percentages;
- duplicate/invalid row counts;
- normalized failure-reason counts; and
- `EvidenceAction`, restricted to `NO_ACTION`.

Metric invariants include:

```text
READY + PENDING + BLOCKED <= risk_rows
PASS + FAILED <= risk_rows
portfolio_eligible <= total_candidates
matched_eligible + missing_risk + metadata_mismatch = portfolio_eligible
SHADOW_READY <= matched_eligible
```

Unknown or inconsistent status rows are counted explicitly rather than forced
into an approved category. Percentages are emitted only with their numerator
and denominator. A zero denominator produces null/N/A.

`metadata.json::EvidenceMetrics` must duplicate the SUMMARY metrics and match
them exactly. This makes a zero-row/detail-free report independently auditable.

# 10. Framework Readiness Criteria

The framework produces evidence; none of its states authorizes a production
migration or trade.

## INSUFFICIENT EVIDENCE

Use when any required scenario, file, metadata field, source hash,
point-in-time proof, replay, metric, or failure reason is absent or invalid.
Also use when only synthetic evidence exists for the proposed operational
observation period.

Required action: preserve no-action state, retain the production boundary, and
collect or correct evidence without overwriting prior snapshots.

## SHADOW VALIDATED

Use when:

- all six required scenarios pass with immutable, reproducible evidence;
- schemas, hashes, provenance, point-in-time boundaries, and metric invariants
  validate;
- no unexplained cross-date/run join or artifact change exists;
- zero/pending/failed/mismatch cases remain NO_ACTION; and
- the reviewed observation window and scenario mix satisfy predeclared shadow
  acceptance criteria.

This state approves continued confidence in the shadow framework only. It does
not approve consumer migration.

## READY FOR MIGRATION REVIEW

Use only when SHADOW VALIDATED is achieved and:

- the governance-approved real multi-date observation window is complete;
- coverage, failures, and stability meet criteria declared before observation;
- source/model/version changes during the window are separately revalidated;
- every known anomaly has a disposition and owner; and
- the Phase 6B-7 migration blockers can be presented with complete shadow
  evidence to a separate human migration review.

This state means “sufficient evidence exists for a migration review.” It does
not mean migration approved, production switched, or order approved.

State progression:

```text
INSUFFICIENT EVIDENCE
  -> SHADOW VALIDATED
       -> READY FOR MIGRATION REVIEW
```

States cannot be skipped. New provenance, leakage, reproducibility, or archive
integrity failures return the framework to INSUFFICIENT EVIDENCE. Favorable
scores, trades, returns, or coverage cannot override a failure.

# 11. Multi-Date Observation Plan

Before collection begins, governance must approve:

- observation start/end or minimum decision-date count;
- expected cadence and holiday handling;
- required observed versus controlled-synthetic scenarios;
- acceptable missing-risk/orphan/mismatch rates;
- treatment of model or universe version changes;
- archive owner and read permissions;
- anomaly response and re-run policy; and
- stop conditions.

The observation set must include multiple real AsOfDates and, where available,
multiple market regimes. Date selection must be calendar/rule driven, not based
on later returns or whether the new path looks favorable.

For each snapshot, the collector must either publish a complete immutable
directory or an explicit failed-run log outside the canonical archive. It must
not omit adverse dates. Aggregate review reports every expected date,
including missing snapshots, and separates:

- observed operational evidence;
- controlled scenario fixtures; and
- invalid/quarantined evidence.

# 12. Validation and Test Design for Future Implementation

The future archive implementation requires tests for:

1. creation of the exact directory/file contract;
2. refusal to overwrite an existing AsOfDate;
3. atomic publish and cleanup after pre-publish failure;
4. deterministic RunId and snapshot identity;
5. canonical artifact and metadata hashes;
6. metadata/artifact provenance agreement;
7. missing, extra, modified, or hash-mismatched file rejection;
8. all six required scenarios;
9. stable SUMMARY metrics for zero candidates;
10. metric invariant validation;
11. future OHLCV mutation and append isolation;
12. future portfolio-state rejection;
13. exact-date/run joins with no repair fallback;
14. two-run reproducibility with only approved informational differences;
15. input and prior archive immutability;
16. deterministic multi-date aggregation; and
17. exclusion of production action, sizing, holdings, and legacy risk fields.

Architecture-boundary tests must prove that no active portfolio, position,
order, or daily-decision module imports the archive collector or reads
`shadow_archive/`.

# 13. Current Evidence State and Remaining Work

At design time, the repository has a safe current zero-eligible snapshot and
synthetic unit evidence for single/multiple eligible candidates, READY,
PENDING, BLOCKED, missing risk, and metadata mismatch. It does not yet have the
immutable archive contract, an operational collector, archived real multi-date
snapshots, or a predeclared observation window.

Therefore, the current framework result is:

`INSUFFICIENT EVIDENCE`

Required next steps are a separately approved non-production archive
implementation, scenario and immutability tests, and unbiased multi-date
collection. Production consumers remain unchanged throughout that work.

Design conclusion: trustworthy historical evidence must be harder to alter
than to preserve. A missing date, failed risk row, or metadata mismatch is
information—not an inconvenience to repair after the fact. Until the archive
can prove what was known at each decision date and reproduce the same result,
no migration conclusion should be drawn.
